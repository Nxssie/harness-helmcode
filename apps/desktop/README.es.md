# NaN Harness Desktop

[English](README.md) | Español

La analítica de Desktop sigue la [política de recolección del producto](../../packages/client/product-analytics/README.md), incluido su ajuste vivo de la aplicación. El uso de Web queda excluido. La instalación de actualizaciones espera a su ingesta local de analítica antes de bloquear la admisión de la API y detener el Host. La ingesta tiene un plazo de un segundo; un fallo no impide la instalación, y la entrega al recolector no se espera.

La aplicación de escritorio es un shell de Electron alrededor de la aplicación Web completa de dsh. Un proceso hijo RunAsNode de Electron arranca el runner de perfil compartido, y Electron carga inmediatamente la entrada Web empaquetada en `dsh-app://app/`. Su página de carga compartida espera las inyecciones de arranque del Host y después inicia el cliente sin navegar a otro documento. Electron reenvía las solicitudes HTTP de la aplicación al Host Web autenticado, descartando las cabeceras de respuesta de nivel de conexión (`transfer-encoding`, `connection`, `keep-alive`) que describen el fetch de Node y no el recurso, y marcando las respuestas de bundles de plugins como `no-store` porque sus revisiones por lanzamiento solo se acumularían en la caché de disco de Chromium; los flujos WebSocket se conectan a ese Host con credenciales adjuntas solo para la ventana de aplicación propia. El IPC de Node transporta las inyecciones de arranque, la disponibilidad y el apagado. Desktop usa por defecto el puerto `19387`, distinto del `3080` de Web; un parche `webserver.config.port` puede anularlo.

El primer comando del menú de aplicación, **Acerca de NaN Harness**, abre el panel Acerca de nativo de Electron con el icono de la aplicación, el nombre del producto y la versión de lanzamiento instalada. El menú sigue la locale del shell de Desktop. En macOS, Ocultar, Ocultar otros, Mostrar todo y Salir usan etiquetas localizadas; Ocultar y Salir incluyen el nombre de producto NaN Harness. Estos comandos conservan sus acciones y atajos nativos. macOS lee el icono de su bundle de aplicación, por lo que un lanzamiento de desarrollo sin empaquetar muestra el icono de Electron; Windows recibe el PNG empaquetado.

El flujo de directorio nativo local de Desktop abre un diálogo de carpetas de Electron adjunto a la ventana de la aplicación, restaurando, mostrando y enfocando primero esa ventana. Las solicitudes concurrentes comparten un solo diálogo; la cancelación no devuelve ninguna ruta y los fallos siguen siendo reintentables. Web ordinario usa el selector del Host. El modo de exploración lista los directorios del Host. En Linux sin zenity ni kdialog, la selección automática usa la exploración en lugar del diálogo de Electron.

Creator y el gestor de plugins de Web usan el pnpm incluido de Desktop bajo el modo Node de Electron sin requerir pnpm en PATH. El entorno privado del lanzador Node se aplica solo a las operaciones de paquetes.

Los documentos de Platform incrustados usan una partición persistente de WebContentsView indexada por un hash del origen de Platform y del ID de cuenta estable. Las preferencias de localStorage, incluidos los avisos descartados, sobreviven al cierre de la vista y al reinicio de la aplicación; las cuentas y los orígenes distintos usan almacenamientos separados. El Host aporta el ID de cuenta de su última lectura de perfil con éxito; mientras no se conoce ningún ID, el documento se abre en una partición desechable que no conserva ninguna preferencia entre aperturas. Al abrir una partición persistente se limpian las cookies, el sistema de archivos, IndexedDB, Cache Storage, las cachés HTTP y de shaders, los service workers y la autenticación HTTP antes de que el documento cargue; una partición desechable limpia todo su almacenamiento. Al cerrar una vista se destruye el documento, se eliminan sus interceptores de solicitudes y se programa la misma limpieza, por lo que la autenticación dejada por una salida incorrecta se limpia antes de que cargue el siguiente documento. La siguiente apertura y el apagado de la aplicación esperan esa limpieza, y una instalación de actualización la espera antes de que el instalador tome el control de la salida. Una limpieza fallida rechaza esa apertura y bloquea la misma cuenta hasta que una limpieza posterior tenga éxito; las demás cuentas siguen abriéndose. Cerrar sesión destruye el documento pero conserva las preferencias del ámbito de la cuenta para el siguiente inicio de sesión. Un documento ya abierto en una partición desechable permanece montado cuando llega el ID de cuenta para la misma credencial; la siguiente apertura usa la partición del ámbito de la cuenta. La [decisión de almacenamiento](../../.agents/notes/implemented/architecture/2026-09-22-platform-browser-storage.md) describe la política de retención. El Host envía las credenciales de cuenta a través de IPC privado de Node; el RPC de cuenta y el renderer de Harness no reciben ningún token. Antes de que se ejecuten los scripts de la página, el preload de Platform realiza un IPC síncrono para leer la credencial preparada del proceso principal. Expone displayMode, los getters síncronos getAuthToken() y getLocale(), y onLocaleChange(listener), que devuelve una función de cancelación de suscripción. Ambos getters leen la memoria del preload sin más IPC. El bootstrap incluye el idioma de Desktop resuelto (`es_ES` o `en_US`); los cambios de idioma de la configuración actualizan la caché del preload y notifican al documento de Platform abierto sin recargar. Platform aplica este idioma antes de su primer renderizado y no lo persiste como preferencia del navegador. El manejador del proceso principal solo realiza la validación del emisor y una lectura en memoria; nunca espera al Host, al disco ni a la red. Los fallos de inicialización de páginas confiables conservan el modo incrustado y hacen que el getter lance una excepción, impidiendo el fallback a credenciales del navegador. Solo el frame principal de Platform propio en el origen del emisor configurado puede inicializarse. Cerrar sesión, reemplazar la credencial, apagar el Host y cerrar la vista destruyen el documento. La navegación de documentos entre orígenes está bloqueada. Los enlaces HTTPS que solicitan una ventana nueva se abren en el navegador del sistema sin la sesión incrustada ni el token; los demás esquemas y las credenciales en URL se rechazan. Las vistas nativas ocupan el viewport bajo la barra de retorno de la funcionalidad de cuenta.

Las solicitudes del Host de Desktop a la API de Platform y las solicitudes de política de actualización identifican el cliente instalado con las mismas cabeceras de cliente de Platform: plataforma, versión del cliente, locale, desplazamiento de zona horaria en segundos y un bundle id intencionadamente vacío. Las operaciones de cuenta toman la identidad de la UI llamante por llamada; el proveedor de cuentas posee la [configuración de cabeceras solo de API](../../packages/credentials/deepseek-account-platform/README.md#use-this-package). La política de actualización reporta además la arquitectura, el canal de actualización y la versión del runtime incluido.

Una credencial de cuenta expirada en el servidor vuelve a Welcome cuando no hay ninguna clave de API oficial configurada; una clave de API disponible mantiene el espacio de trabajo abierto. El cierre de sesión explícito sigue la misma regla. Tanto Welcome como el espacio de trabajo muestran el aviso de expiración localizado.

El acceso al micrófono de Desktop está restringido a las solicitudes de audio del frame principal `dsh-app://app`. macOS usa la autorización de micrófono del sistema, una descripción de uso empaquetada y `com.apple.security.device.audio-input` en las firmas de la aplicación principal y del Helper.

Pulsar F12 (Fn+F12 en teclados con teclas multimedia), Command+Option+I en macOS, o Ctrl+Shift+I en Windows para alternar las DevTools de la página de aplicación enfocada, incluido en compilaciones empaquetadas. Estos atajos nativos usan elementos ocultos del menú de aplicación. Los overlays de actualización y los invitados de navegador incrustado empaquetados deshabilitan las DevTools.

## Comando de terminal

La entrada **Gestionar el comando dsh…** del menú de aplicación, inmediatamente bajo **Buscar actualizaciones…**, muestra el comando actual y ofrece Instalar, Reparar y Eliminar. El comando usa el runtime instalado de Desktop y la [CLI dsh](../cli/README.es.md) ordinaria, incluso cuando la aplicación Desktop está cerrada. Abrir una terminal nueva tras la instalación y ejecutar `dsh --version`.

En macOS, la instalación crea `/usr/local/bin/dsh` y solicita autenticación de administrador cuando el directorio lo requiere. Los archivos de inicio del shell no se modifican. En Windows, el diálogo de gestión registra el comando en el PATH del usuario actual. Linux no ofrece instalación del comando. Un comando preexistente requiere confirmación antes de cambiarlo; reparar el propio comando seleccionado de Desktop no repite esa confirmación. El enlace de macOS preserva y restaura el lanzador desplazado; Windows preserva las demás entradas de PATH, incluidas las anteriores al registro. Un comando con mayor precedencia en PATH se reporta con su ubicación. Tras mover la aplicación, usar Reparar en macOS o Instalar desde la nueva ubicación en Windows. Eliminar deja intactas las instalaciones no relacionadas.

El registro del comando es opcional tras instalar Desktop. Usar **Gestionar el comando dsh… → Eliminar** antes de desinstalar Desktop para quitar su registro de la CLI; el desinstalador de la aplicación no lo quita. Terminar los comandos de la CLI antes de actualizar o desinstalar Desktop. La versión del runtime de la CLI sigue al lanzamiento de Desktop instalado. Ver [runtime del comando incluido](#bundled-command-runtime) para los comandos de plugins de Desktop y las limitaciones del runtime.

## Cerrar la ventana y salir

Cerrar la ventana principal (el botón de cierre de macOS y ⌘W; ×, Alt+F4 y el comando Cerrar ventana de la barra de tareas en Windows) la oculta; Windows pide confirmación antes del primer ocultado. La página y el Host siguen en ejecución, las tareas continúan, y la siguiente reaparición presenta el mismo documento con su sesión, borradores y posición de scroll; una ventana de macOS a pantalla completa sale de la pantalla completa antes de ocultarse. La ventana vuelve a través del icono del Dock, un segundo lanzamiento o `dsh://open` en macOS, y a través de la bandeja en Windows. Minimizar no cambia. Cerrar la ventana de bienvenida antes de que se abra el espacio de trabajo sale de la aplicación en Windows y, en macOS, mantiene la aplicación en el Dock sin ventana.

Windows mantiene un icono de bandeja durante toda la ejecución. Su tooltip es el nombre del producto, un solo clic muestra y enfoca la ventana, y el menú contextual ofrece Abrir NaN Harness y Salir de NaN Harness en la locale del shell. Antes del primer ocultado, el overlay de diálogo de actualización compartido explica que las tareas en ejecución continúan y que la ventana puede reabrirse desde la bandeja del sistema. Confirmar oculta la ventana y escribe `background-close-confirmed` bajo el userData de Electron; Escape, descartar el diálogo o un fallo del diálogo mantiene la ventana visible y no registra la confirmación. Las solicitudes de cierre repetidas enfocan el diálogo del shell existente. Las actualizaciones en el lugar conservan el marcador y la desinstalación lo elimina. El antiguo marcador `background-notice-shown` no suprime esta confirmación. Cerrar la ventana no envía ninguna notificación del sistema. Los bitmaps de la bandeja son `resources/tray-windows.ico`, renderizados desde `resources/icon-windows.svg` a 16, 20, 24, 32, 40, 48 y 64 píxeles por `pnpm run render:tray-icon`, y empaquetados como `resources/tray.ico`. macOS no distribuye icono de barra de menús.

Cada entrada ordinaria de salida (⌘Q, el menú de aplicación, el menú del Dock, la bandeja de Windows y el menú Aplicación del título, y las salidas causadas por cerrar la ventana de actualización obligatoria o de bienvenida) pregunta al Host qué interrumpiría. El Host responde por el canal IPC privado con dos hechos: las tareas activas bajo la misma regla que la comprobación de reinicio por actualización (agents en ejecución incluidos subagents y esperas de aprobación, mensajes en cola, jobs en ejecución o deteniéndose), y los recordatorios programados armados reportados por la familia `schedule` de `workspace/session-activity` para las sesiones cargadas durante esta ejecución. Sin ninguno de los dos hechos, la salida prosigue en silencio. En caso contrario, un cuadro de mensaje nativo sin ventana propietaria (las ventanas ocultas permanecen ocultas) muestra **¿Salir de NaN Harness?** con una de tres explicaciones localizadas: las tareas en ejecución se interrumpirán, las tareas programadas no se ejecutarán mientras la aplicación esté cerrada, o ambas. Salir es el botón por defecto y Cancelar responde a Esc; macOS coloca Cancelar a la izquierda de Salir, Windows coloca Salir a la izquierda de Cancelar, y el diálogo de tarea de Windows muestra el icono de la aplicación y permanece claro con independencia del tema de la aplicación. Un Host que no ha alcanzado el estado listo o ha fallado no puede ejecutar tareas, por lo que la salida prosigue sin preguntar. Un fallo de inspección o un Host que no cumple el plazo de dos segundos se trata como tareas en ejecución. Mientras el cuadro está abierto, otra solicitud de salida se une a él en lugar de apilar una segunda (macOS también lo eleva; Electron no expone ningún identificador del diálogo de tarea de Windows), la explicación no cambia cuando el trabajo empieza o termina, Salir detiene la aplicación sin reinspeccionar, y Cancelar no cambia nada. Cancelar una salida iniciada al cerrar la ventana de bienvenida vuelve a mostrar la ventana de bienvenida.

La confirmación de actualización obligatoria incluye el aviso de espera de instalación en Windows; macOS usa la explicación de reinicio más corta.

La confirmación se omite cuando el reinicio del instalador ya confirmó la interrupción de tareas, cuando el diálogo de recuperación fatal sale o reinicia, cuando se ejecuta el comando de desarrollo Reiniciar app y Host, y durante el apagado, reinicio o cierre de sesión del sistema operativo: Windows lo establece en el mensaje definitivo de fin de sesión; macOS lo establece en la notificación de apagado y, como otra aplicación aún puede cancelar ese apagado, el siguiente enfoque o muestra de la ventana principal lo limpia. La salida propiedad del instalador cancela cualquier decisión de salida ordinaria pendiente; los resultados de inspección tardíos y las respuestas del diálogo no pueden abrir otra confirmación ni repetir la limpieza. Una descarga de actualización iniciada por el usuario que termina mientras la ventana está oculta difiere su confirmación de Instalar y reiniciar hasta que la ventana se muestre de nuevo; el flujo obligatorio mantiene su atención en la barra de tareas y el Dock. El instalador y el desinstalador de Windows indican a un usuario cuya aplicación sigue en ejecución que la cierre desde la bandeja del sistema. Desktop no habilita las tareas programadas por defecto, por lo que las explicaciones de tareas programadas solo aparecen una vez activada esa funcionalidad; los recordatorios solo se disparan en sesiones cargadas, y las sesiones no cargadas ni se cuentan ni se reanudan hasta que se abren.

El renderer de la bandeja amplía la marca un 20 % alrededor del centro del mosaico preservando el fondo y la relación de aspecto; los iconos de la aplicación y del instalador conservan sus proporciones originales.

## Decisiones técnicas clave

Las ilustraciones originales viven en `resources/icon.png` y `resources/icon.svg`; las adaptaciones por plataforma conservan la marca y los degradados en `resources/icon-windows.*` y `resources/icon-macos.*`. Exportar cada SVG de plataforma como un PNG transparente de 1024×1024. Electron-builder genera el ICO multitamaño para la aplicación, el instalador y el desinstalador de Windows ([requisitos de iconos de Windows](https://learn.microsoft.com/en-us/windows/apps/design/iconography/app-icon-construction)). Las páginas de instalación usan ilustraciones a juego en ambos temas; las páginas de bienvenida y final del desinstalador comparten `installer/assets/uninstaller-sidebar.png`, convertido a un BMP de 164×314 durante la preparación.

Los overrides de atajos se almacenan en `app.getPath('userData')/keybindings.json`, separados de `DSH_HOME`. El proceso principal valida y serializa los cambios antes de publicar las vinculaciones aceptadas. Las lecturas fallidas conservan las últimas vinculaciones aceptadas y bloquean las ediciones, incluida Restaurar todo; los archivos ilegibles y los de versión futura permanecen sin cambios. El desarrollo puede aislar estas preferencias con `DSH_DESKTOP_USER_DATA_DIR`; el lanzador imprime su ruta resuelta. Ver el [servicio de atajos](../../packages/client/shortcuts/README.md) para el formato y la semántica de conflictos.

El menú Archivo de macOS muestra la vinculación de tecla única aceptada, incluidas las teclas de flecha, y enruta Cerrar página o ventana a través del propietario de la página del cliente. En Windows y macOS, todas las vinculaciones completas aceptadas se interceptan antes de la entrada del documento principal, de los frames incrustados y de los invitados de navegador, incluida la entrada de edición y de terminal. La grabación y la composición de métodos de entrada permanecen protegidas. Los overlays de actualización bloquean los atajos del producto y la entrega de teclas de edición a la ventana padre y a sus invitados de navegador desde la creación hasta que se cierra el último overlay. Cada apertura o cierre de overlay invalida el estado de acordes pendiente. El proceso principal comparte un único propietario de overlay entre los diálogos de actualización y la entrada de atajos mediante capacidades explícitas de creación y de estado de entrada. Los acordes de dos teclas dejan la pulsación inicial de la primera tecla disponible para la página y no interceptan su liberación; los acordes completos y sus repeticiones se consumen. El renderer deja el despacho de vinculaciones configurables al adaptador nativo. Los acordes no tienen acelerador de menú nativo. Los comandos aceptados se reenvían una vez a través del preload confiable. Linux despacha los atajos del documento principal a través del DOM y reenvía las vinculaciones aceptadas de frames incrustados al resolvedor del cliente. Cerrar la última ventana preserva el ciclo de vida de la aplicación en macOS; Windows sale de la instancia de escritorio y detiene sus tareas. La [decisión de cierre](../../.agents/notes/implemented/architecture/2026-09-21-desktop-page-close-shortcuts.md) registra esta elección de ciclo de vida.

El PNG de macOS usa un fondo redondeado con margen interior para el empaquetado ICNS heredado, con representaciones de hasta 1024 píxeles. Es un icono aplanado, no un documento de Icon Composer. La [guía de iconos de app](https://developer.apple.com/design/human-interface-guidelines/app-icons) de Apple describe capas sin máscara para Icon Composer; esas entradas requieren una exportación de macOS separada y no deben reutilizar la ilustración ICNS redondeada. Verificar la apariencia en el Finder y el Dock en las versiones de macOS soportadas antes del lanzamiento.

### Dependencias del espacio de trabajo incluidas

electron-builder copia solo las `dependencies` del manifest en `app.asar/node_modules`, por lo que el bundle principal de Electron `lib/main.js` incrusta en línea las devDependencies del espacio de trabajo y deja `electron`, los builtins de Node y esas `dependencies` como sus únicas importaciones bare; un preload con sandbox solo puede dejar `electron`, `events`, `timers` y `url`, los módulos que resuelve su polyfill de `require`. El bundle principal resuelve los paquetes en línea desde su salida `lib/`, por lo que el `build:lib:host` raíz empaqueta `apps/desktop` después de la pasada tsdown concurrente del espacio de trabajo, y [`desktop-bundle-imports`](scripts/desktop-bundle-imports.mjs) hace fallar cualquier bundle de Desktop cuya importación estática, dinámica o `require()` la aplicación empaquetada no pueda resolver. Sin esa comprobación, una importación que rolldown no pudo resolver se distribuye como especificador externo y falla en el lanzamiento con `ERR_MODULE_NOT_FOUND`. La [decisión de orden de bundles](../../.agents/notes/implemented/process/2026-09-22-desktop-main-bundle-after-workspace-tsdown.md) registra las alternativas.

El empaquetado firmado de Windows escanea el runtime principal y las dependencias de producción de la aplicación en busca de contenido PE, incluidos archivos sin una extensión convencional. El escaneo final cubre toda la aplicación desempaquetada. Los enlaces de directorio, los archivos `MZ` malformados y los archivos `.exe`, `.dll` o `.pyd` que no son PE detienen el empaquetado; los archivos de datos que empiezan por `MZ` también se rechazan salvo que contengan una cabecera PE válida. Preserva las firmas válidas del proveedor y firma el código sin firmar antes de sellar los hashes del runtime o ejecutar las pruebas de humo. La inspección de claves públicas usa lotes de 32 archivos con como máximo cuatro procesos; la firma con token hardware permanece serial, y cada firma nueva debe coincidir con el certificado configurado y llevar una marca de tiempo. Los fallos de firma y verificación hardware detienen la ejecución; las solicitudes aisladas de marca de tiempo siguen la política acotada de más abajo. Electron-builder preserva los ejecutables de runtime copiados solo tras la verificación de firma y de bytes exactos. Una auditoría final de firmas PE y una prueba de humo del payload ASAR con caché nueva y del Host deben pasar antes de que se escriba el registro de finalización del lanzamiento. Las compilaciones de desarrollo, de solo preparación y sin firma no usan el token hardware y pueden ser bloqueadas por la política de integridad de código de Windows; ningún modo de compilación deshabilita esa política. Pasar las pruebas de humo no establece la compatibilidad con todas las políticas empresariales.

Desktop transporta distribuciones independientes de Python, Node.js y pnpm. Python incluye numpy, pandas, python-docx, python-pptx, openpyxl, Pillow, lxml y XlsxWriter con sus dependencias completas. La tool `load_workspace_dependencies` instala este payload sin conexión en el primer uso bajo `$DSH_HOME/dsh-runtimes/dsh-primary-runtime` (normalmente `~/.dsh/dsh-runtimes/dsh-primary-runtime`) y devuelve rutas absolutas del intérprete, del script de pnpm y de las bibliotecas, más `pythonDistributions`, los nombres y versiones de las distribuciones incluidas. El informe de versiones excluye las adiciones instaladas por el usuario. Las tareas de Office prefieren estas bibliotecas salvo que las instrucciones del usuario o del espacio de trabajo seleccionen otro entorno. Ejecutar el script de pnpm con el ejecutable de Node devuelto. El directorio de bibliotecas de Node devuelto está reservado para las bibliotecas incluidas, no es el directorio de instalación global de pnpm.

Desktop registra `office-docx`, `office-pptx` y `office-xlsx` por defecto. Las skills (habilidades) usan las bibliotecas Python incluidas para la creación y las ediciones enfocadas, después reabren los archivos y ejecutan un comprobador estructural compartido antes de la entrega. La creación y edición de PowerPoint usa python-pptx. Los recursos de las skills se copian a `runtime/office-skills` fuera del ASAR para que Python pueda leer el comprobador. Una tool `render_document` disponible puede añadir inspección visual; su ausencia no impide la autoría ni la entrega. Ver el [paquete de skills de Office](../../packages/skill/skill-office/README.md) para las comprobaciones y limitaciones.

El payload sigue al lanzamiento de Desktop. `runtime.json` registra la versión de Desktop, el destino, las versiones de nivel superior del intérprete y del gestor de paquetes y el mapa de distribuciones de Python, además de un digest de las entradas de payload bloqueadas del destino seleccionado y del formato de ensamblado. Los nombres de distribución usan la normalización PEP 503; los nombres normalizados duplicados rechazan el manifest. Los manifests `components` heredados siguen siendo legibles mediante normalización, con sus comprobaciones existentes de consistencia de versiones de bibliotecas. Las instalaciones coincidentes se reutilizan; un cambio de dependencia o de archivo reemplaza el directorio tras una copia completa preparada incluso cuando la versión de Desktop no cambia. Los manifests más antiguos sin digest se reemplazan en su siguiente instalación. Los paquetes Python añadidos por el usuario permanecen solo mientras la identidad del payload coincide. Un reemplazo de directorio fallido conserva la instalación anterior; Windows puede rechazar el reemplazo mientras un intérprete sigue en ejecución.

El directorio privado `runtime/bin` de Desktop se añade solo a los procesos de instalación de paquetes, no al PATH del Host heredado por los shells de PTC y del agent. Esta tool no cambia PATH, variables de entorno ni la configuración del gestor de paquetes del usuario. pnpm conserva sus propios valores por defecto y ajustes de usuario para los paquetes globales, las entradas ejecutables y su store, incluidos los errores nativos cuando el entorno no soporta la instalación global. No hay un actualizador de dependencias separado. [La decisión del runtime primario](../../.agents/notes/implemented/feature/2026-09-14-desktop-primary-runtime.md) registra estas elecciones.

Node prepara los intérpretes y las bibliotecas Python incluidos sin un Python de sistema ni pip. [El lock de descarga](../../scripts/primary-runtime/lock.json) fija los archivos de intérprete, las versiones de distribución de Python y las URL y hashes de wheel específicos del destino; el constructor compartido resuelve pnpm desde el pin de dependencia de desarrollo raíz. La versión del gestor de paquetes raíz y el pin de Desktop se comprueban mutuamente. Los nombres de archivo wheel y las versiones de distribución deben coincidir para cada destino. Preservar el orden de claves dentro del destino seleccionado, los registros de wheel y el mapa de distribuciones, además del orden de las entradas wheel; afectan a la identidad del payload, mientras que el orden de claves de nivel superior del lock no. Los wheels de bibliotecas se desempaquetan en site-packages, conservando los archivos auxiliares bajo el directorio `.data/scripts` de cada wheel sin generar scripts envoltorio de comandos. Los demás esquemas de instalación se rechazan. Las comprobaciones de destino nativo verifican el conjunto y las versiones de wheels bloqueados, permiten el pip incluido del intérprete y comprueban la versión de Python, las operaciones de lectura y escritura de documentos Office y la completitud de dependencias sin escribir bytecode tras la limpieza de preparación y de nuevo tras la firma de macOS. El ejecutable de Node independiente recibe el entitlement JIT requerido por V8; el destino x64 también recibe `com.apple.security.cs.allow-unsigned-executable-memory` para las páginas de código ejecutable, incluido bajo Rosetta. Node ARM64 y los helpers de Office conservan solo permisos JIT. La ejecución entre destinos y la instalación firmada requieren el host de lanzamiento del destino. Tanto `dev:desktop` como `start:desktop` preparan `.desktop-build/targets/<target>/runtime/primary-runtime` antes de lanzar Electron; el primer uso puede descargar dependencias bloqueadas. Una preparación sin terminar no puede reportar una salida con éxito del lanzador.

| Decisión | Por qué | Consecuencia directa |
|---|---|---|
| Identidad de lanzamiento | La API del shell, el cliente Web, el backend y el grafo de plugins se cualifican como una sola combinación; las versiones independientes crearían combinaciones no probadas y una disponibilidad de actualizaciones ambigua. | Electron y `@deepseek-ai/dsh` siempre tienen exactamente la misma versión. Una actualización de dsh es un lanzamiento de Desktop, incluso cuando el código del shell no cambia. |
| Runtime | La aplicación debe ejecutarse sin una instalación de Node.js o pnpm del sistema. | dsh se ejecuta bajo Electron con `ELECTRON_RUN_AS_NODE=1` y `--expose-internals`, y cada operación de paquetes usa el pnpm incluido. La configuración del gestor de paquetes y el entorno del Host siguen los ajustes del usuario. Los scripts de paquetes usan un lanzador de shell `node` que reenvía a Electron. |
| Fuentes de paquetes | La instalación del núcleo en el arranque añade trabajo incluso sin conexión. | `app.asar/dsh` transporta un árbol completo de dependencias de producción; el perfil solo instala plugins externos. |
| Propiedad del estado | Compartir grafos de dependencias ejecutables permitiría a la CLI y a Desktop cambiar mutuamente sus versiones de dsh, Cordis, plugins o módulos nativos, mientras que dos procesos de escritorio podrían competir por el mismo perfil. | Electron adquiere su bloqueo de instancia única de por vida del proceso antes de cualquier acceso al perfil y posee en exclusiva `$DSH_HOME/profiles/desktop` más su estado de gestor de paquetes. La CLI y Desktop comparten los datos de producto soportados bajo `$DSH_HOME`, pero nunca paquetes ejecutables, activación de plugins, lockfiles ni `node_modules`. |
| Transporte | El servicio Web y la autenticación comparten una implementación. | Electron carga los assets Web empaquetados; el Host aporta las inyecciones de arranque y las API autenticadas. |
| Cambios de plugins | Desktop y Web necesitan el mismo comportamiento de instalación y activación. | La aplicación principal usa el gestor de plugins de Web compartido y el pnpm incluido. |
| Actualizaciones | Las actualizaciones independientes del shell y de dsh recrearían divisiones de versiones, mientras que los bloques de shell sin cambios no deberían requerir una transferencia completa. | El shell de Electron, el runtime de dsh correspondiente y pnpm forman una única unidad de actualización firmada. Los artefactos de actualización de Platform pueden reutilizar bloques sin cambios, pero la selección de la versión de runtime nunca se separa del lanzamiento de Desktop. |

La [decisión del envoltorio fino](../../.agents/notes/implemented/architecture/2026-09-10-desktop-web-wrapper.md) posee el comportamiento Web compartido y los adaptadores de Desktop. La [decisión de empaquetado y actualización de Electron](../../.agents/notes/implemented/architecture/2026-08-25-electron-desktop-packaging-and-updates.md) posee la identidad de lanzamiento, la firma y la cualificación de actualizaciones.

Welcome carga la paleta de Toast compartida y los tokens de sombra, con tipografía del sistema para las notificaciones montadas en el body.

## Runtime del comando incluido

El script de shell instalado `resources/runtime/cli/bin/dsh` (`dsh.cmd` en Windows) ejecuta el despachador ordinario de la CLI usando el ejecutable de Electron de Desktop y el pnpm incluido. Funciona mientras Desktop está cerrado y conserva las [limitaciones del runtime de Electron](../../.agents/notes/implemented/architecture/2026-09-11-desktop-electron-node-runtime.md). Los comandos ordinarios de perfil, configuración y plugins usan la misma implementación que el dsh de npm; el comando no abre Desktop.

Para gestionar los plugins de Desktop, lanzar Desktop una vez para inicializar su perfil, salir por completo de la aplicación, y después ejecutar `dsh plugin --profile desktop add <package>`, `list` o `remove <package>`. Reabrir Desktop para usar los cambios. Las operaciones de paquetes conservan el bloqueo de escritura de perfil compartido y las comprobaciones de compatibilidad. El comando instalado rechaza un perfil de Desktop sin inicializar en lugar de crear un perfil ordinario de la CLI en su lugar.

Terminar los comandos de la CLI antes de actualizar o desinstalar Desktop; el instalador no se coordina con los comandos en ejecución. La CLI no aporta rutas de recursos de las skills de autoría de Office. La configuración de Office existente de Desktop y la conversión de adjuntos de Web conservan su propia configuración de recursos. `prepare:runtime` copia los scripts de lanzamiento sin compilar un lanzador nativo de la CLI.

## Propiedad de la instalación

Electron posee `$DSH_HOME/profiles/desktop`. Sus `dependencies` contienen los paquetes instalados por pnpm; `dsh.profile.bundles` contiene los bundles incorporados seguidos de los plugins habilitados. La aplicación firmada aporta dsh, el Host privado de Desktop y sus paquetes de producción desde `resources/app.asar/dsh`. Las aplicaciones empaquetadas seleccionan la resolución de perfil en runtime sin crear enlaces de paquetes; los perfiles de desarrollo usan enlaces del sistema de archivos. Tanto el host como los plugins se ejecutan en el mismo proceso Electron en modo Node; Desktop no habilita `--preserve-symlinks`. La CLI no puede arrancar este perfil. El comando instalado por Desktop puede gestionar sus plugins mientras la aplicación está cerrada; el dsh instalado por npm no puede mutarlo.

El preload de la aplicación expone la disponibilidad de arranque, el reporte de arranque fatal, la selección nativa de directorios, el puente `__DSH_HOST_PATHS__` para las referencias de rutas del composer y el puente Browser de ámbito de lease solo a los documentos `dsh-app://app`. El mismo preload reenvía la descripción de máquina del proceso principal desde `dshDesktop.deviceInfo()` como campos `name=value` separados por `; `: `platform`, `os`, `app_arch` (la arquitectura con la que se ejecuta el binario de la aplicación, que difiere de la arquitectura hardware bajo emulación), `cpu` y `memory_gib` (memoria física total en GiB con un decimal). Un campo se omite cuando su fuente no está disponible. La descripción no lleva nombre de host, nombre de usuario ni número de serie. Los documentos del producto usan las API HTTP autenticadas compartidas y reciben el marcador de Desktop, la presentación de actualizaciones y una acción que abre la confirmación nativa; no pueden elegir artefactos ni autorizar la instalación. La gestión de plugins usa las API HTTP autenticadas de la aplicación Web. Electron sirve los documentos y assets del diálogo de actualización localmente en `dsh-app://shell/`, independientemente de la disponibilidad del Host. Electron no expone IPC de gestión de plugins ni un documento de gestión separado. Ningún renderer recibe acceso al sistema de archivos, IPC crudo de Electron, un shell ni argumentos arbitrarios de pnpm.

Solo la ventana principal de la aplicación habilita `<webview>`. El adjunto de invitados debe coincidir con un lease y una partición emitidos por la principal; los invitados conservan sandbox, aislamiento de contexto y seguridad Web sin integración de Node ni preload de invitado. Los listeners IPC de Browser se crean solo para el documento de la aplicación. [Sidebar Browser](../../packages/client/ui-sidebar-browser/README.md) describe la agrupación de almacenamiento y las limitaciones de los invitados; la autenticación del Host sigue siendo necesaria independientemente del filtrado de URL.

El origen `dsh-app://shell/` sirve documentos, scripts y estilos de actualización empaquetados sin contactar con el Host. Las solicitudes estáticas conservan el manejo de GET/HEAD, la contención de rutas y el MIME; cada documento de actualización mantiene su preload aislado y las comprobaciones de IPC de ventana propia.

La UI del producto conserva las acciones de Web, incluida «Open In...» a través de las rutas HTTP autenticadas compartidas. Desktop usa la selección automática de selector de directorios de Web e inicializa los perfiles nuevos con los bundles de la plantilla Web compartida.

El texto de actualización preserva la versión completa, incluidos los sufijos de prelanzamiento, sin añadir v ni V. Cuando no hay ninguna actualización disponible, el título del diálogo reporta el resultado y el cuerpo muestra la versión actual.

Electron elige texto de shell tipado en inglés o español a partir de la locale de su aplicación y recurre al inglés como fallback. El bundle de aplicación de macOS declara inglés y español en `CFBundleLocalizations`, permitiendo a macOS hacer coincidir el idioma inicial de la aplicación con los idiomas preferidos del usuario. Las preferencias de idioma guardadas de la UI de cliente siguen teniendo precedencia para la interfaz principal. En Windows, el idioma del documento principal actualiza los menús de escritorio y los avisos de recuperación y actualización. La puerta de i18n de la UI de cliente del repositorio comprueba las fuentes de escritorio.

Windows y macOS retransmiten las transiciones nativas de pantalla completa y el estado tras cada carga de página al renderer, para que los overlays puedan adaptar su margen del título.

Windows usa un título de 40 DIP con controles de ventana nativos y colores sincronizados desde la paleta de la aplicación. Las entradas localizadas Aplicación y Edición junto al botón de la barra lateral abren menús emergentes nativos. Se montan solo después de que el frame de la aplicación publica su asiento de overlay del shell, y permanecen ausentes durante la carga de arranque. Aplicación ofrece Buscar actualizaciones y Salir; Edición ofrece deshacer, rehacer, cortar, copiar, pegar, eliminar y seleccionar todo enviando las teclas correspondientes al editor enfocado, independientemente de las vinculaciones de atajos personalizadas. La gestión de plugins usa la página de plugins de la aplicación principal. Ninguna fila de menú nativa separada aparece con Alt. Las demás plataformas conservan sus menús nativos. Los campos editables conservan los comandos de teclado y un menú contextual sin etiquetas de atajos; Chromium aporta la disponibilidad de comandos, y el texto de solo lectura seleccionado ofrece Copiar.

En macOS el menú personalizado conserva el menú Ventana estándar de Electron y los comandos de ocultación de la aplicación, incluidos Minimizar (⌘M) y Ocultar (⌘H). Linux conserva los menús de aplicación y Edición.

### Runtime y activación de plugins

El `resources/app.asar/dsh/desktop-runtime.json` firmado vincula la versión del shell, la versión de Node de Electron, la plataforma, la arquitectura, las versiones de paquetes compartidos y el inventario final de archivos. El arranque lee los metadatos y comprueba los registros de paquetes compartidos. El schema de lanzamiento, la versión del shell, la compatibilidad del destino y la integridad de los archivos se verifican durante el empaquetado. Los paquetes del núcleo nunca se copian al almacenamiento del perfil ni los instala pnpm en el primer lanzamiento.

1. La ventana principal carga la página de carga Web compartida fuera de pantalla desde los assets estáticos empaquetados antes de la preparación del perfil o el arranque del backend. La inicialización de perfil compartida crea el manifest ausente, un parche de usuario vacío y los archivos del espacio de trabajo de pnpm sin sobrescribir los archivos existentes.
2. Antes del arranque del Host, Desktop valida el descriptor de runtime y prepara el perfil sin modificar los paquetes instalados, las declaraciones ni el lockfile; solo elimina las proyecciones `.dsh-module-fallback` que escribieron los lanzamientos anteriores del backend de enlaces, y el arranque nunca ejecuta pnpm. Los paquetes dentro del perfil conservan la precedencia nativa, y los nombres de paquetes de la instalación se resuelven a través de la resolución de runtime ([orden de búsqueda](../../.agents/notes/implemented/architecture/2026-09-19-profile-resolution-lookup-order.md); [eliminación de limpieza](../../.agents/notes/implemented/simplification/2026-09-19-remove-desktop-profile-core-cleanup.md)).
3. Los cambios en la versión de Node de Electron, la plataforma o la arquitectura preservan los plugins instalados. Las incompatibilidades nativas afloran durante la carga y pueden repararse mediante pnpm.
4. La página de plugins de la aplicación principal usa el [gestor de plugins](../../packages/boot/plugin-manager/README.md) compartido contra el perfil de Desktop. Las operaciones de paquetes usan el pnpm incluido con la configuración normal de usuario y perfil.
5. El gestor compartido posee los errores de instalación, la activación y los requisitos de reinicio. La recuperación nativa puede deshabilitar bundles de terceros incluso cuando el Host no puede arrancar.

La [UI de plugins de Web](../../packages/client/ui-plugin-manager/README.md) posee la interfaz de gestión. La inicialización y recuperación del perfil de Desktop preservan los archivos de plugins instalados.

Los fallos fatales de creación de la ventana principal, carga del documento principal, preload, renderer, inicialización Web o backend abren un diálogo nativo de recuperación por proceso de aplicación. Muestra una cola acotada del primer error, señala cualquier truncamiento, y ofrece Salir, Reiniciar y Deshabilitar los plugins de terceros, respaldar el parche del perfil y reiniciar. Los fallos de arranque conservan la página de carga Web y el spinner; los fallos en runtime conservan la página actual. Los apagados esperados, la navegación cancelada y las solicitudes ordinarias no disparan la recuperación. El gestor de plugins de Web compartido reporta los errores de operaciones de paquetes; los fallos de arranque del Host tras cambios de plugins entran en la recuperación nativa. No hay heurística de timeout de arranque. Un fallo de listener que contiene `listen EADDRINUSE` reemplaza los diagnósticos y el consejo de reinstalación por la orientación de salir de otras instancias de DSH en ejecución, y ofrece solo Salir y Reiniciar.

Los detalles del diálogo nativo incluyen como máximo 1 200 unidades de código UTF-16 y ocho líneas de diagnóstico, más la ruta del reporte de fallo descrito abajo cuando se escribió uno. Los diagnósticos de error del Host conservan solo los últimos 64 Ki caracteres escritos en stderr. La salida anterior se descarta para que un Host de larga duración no haga crecer el búfer de diagnóstico del shell indefinidamente.

Antes de que se abra el primer diálogo fatal, Electron escribe un reporte de fallo en el directorio de logs de la plataforma (`app.getPath('logs')`: `~/Library/Logs/NaN Harness` en macOS, `logs` bajo el directorio `userData` de la aplicación en Windows y Linux), esperando como máximo un segundo a la escritura; una escritura lenta o fallida muestra el diálogo sin ruta. El archivo `crash-<UTC time>-<source>.log` registra el origen (`host` para una salida del Host, `web-boot` para un fallo de arranque del renderer, `renderer` para un fallo del renderer o del documento, `main` para un error del shell), si el backend había alcanzado el estado listo, las versiones de la aplicación y del runtime, el error con sus propiedades enumerables y cadena de causas (cortado a 256 KiB), el propio error inspeccionado del Host (como máximo 64 KiB) cuando el Host reportó un fallo de arranque por IPC antes de salir, y la salida reciente de consola de nivel error de la ventana principal (como máximo 64 KiB). Un reporte de salida del Host contiene por tanto la cola de stderr conservada, que puede incluir salida de plugins. Un fallo fatal durante el apagado escribe un reporte sin abrir un diálogo. Los archivos son solo del propietario donde la plataforma lo soporta; el arranque conserva los diez reportes más recientes y elimina los más antiguos sin tocar otros archivos del directorio.

La recuperación espera al apagado del Host antes de cambiar la activación de plugins. La acción nativa de recuperación llama a la función de recuperación de app-boot compartida bajo el bloqueo de transacción del perfil. Deshabilita los bundles de terceros y renombra el `cordis.patch.yml` del perfil a `cordis.patch.yml.bak-<timestamp>` (con un ordinal en las colisiones) sin analizarlo; el siguiente arranque crea un parche vacío. Los paquetes instalados y los respaldos anteriores permanecen. El parche de nivel home no cambia. La consola de Electron registra la ruta del respaldo (o su ausencia) y el parche de nivel home sin cambios. Los datos de perfil inválidos, los fallos de renombrado o los fallos de escritura se reportan como errores de la operación de recuperación; los cambios completados permanecen, y Desktop no reinicia como si la recuperación hubiera tenido éxito. Desktop no tiene acción de restablecimiento de perfil ni documento HTML de emergencia.

### Entorno del Host

Los lanzamientos GUI de macOS y Linux heredan solo el entorno del gestor de sesión, sin las variables exportadas por los archivos de inicio del shell. Antes de que arranque el primer Host, Desktop ejecuta el shell de login de la cuenta (de la base de datos de usuarios, no `$SHELL`) una vez como `<shell> -ilc` y lee su salida `env -0` entre delimitadores, de modo que `~/.zprofile` y `~/.zshrc` (o los equivalentes del shell) surten efecto para el Host, los shells del agent, las terminales y la configuración del perfil. La lectura se ejecuta en paralelo con la preparación del perfil. La sonda no tiene entrada de terminal y establece `DISABLE_AUTO_UPDATE=true`, `ZSH_TMUX_AUTOSTARTED=true` y `ZSH_TMUX_AUTOSTART=false` para evitar que los plugins de oh-my-zsh y tmux bloqueen. Los valores del shell reemplazan los valores heredados excepto `PWD`, `OLDPWD`, `SHLVL`, `_`, esas variables de la sonda y los nombres `DSH_*` y `ELECTRON_*` propiedad del lanzador; Desktop resuelve rutas como `DSH_HOME` antes de la lectura, por lo que el Host conserva los mismos valores. La lectura termina en el delimitador de cierre, por lo que los procesos en segundo plano iniciados por los archivos de inicio pueden seguir en ejecución con su salida descartada. Un candidato que no arranca, sale con código distinto de cero, no imprime salida delimitada o excede `DSH_DESKTOP_LOGIN_SHELL_TIMEOUT_MS` (milisegundos enteros de 1000 a 2147483647, por defecto `10000`; su grupo de procesos se mata) se registra como aviso, y Desktop prueba `/bin/zsh`, `/bin/bash` y `/bin/sh` en orden; cuando todos fallan, el Host usa el entorno heredado. El comando de volcado usa sintaxis POSIX, por lo que un shell de cuenta como csh, tcsh o nushell falla y el Host recibe el entorno de los archivos de inicio del primer shell del sistema en su lugar. Salir de Desktop durante la lectura mata el grupo de procesos de la sonda en ejecución. El resultado se lee una vez por proceso de aplicación, por lo que los cambios en los archivos de inicio del shell se aplican tras salir y reabrir Desktop. Los lanzamientos GUI de Windows ya heredan las variables de entorno de usuario y de sistema del registro, por lo que Windows omite este paso.

## Desarrollo

El menú de aplicación de desarrollo ofrece Recargar página (Cmd+R en macOS, Ctrl+R en otras plataformas) y Reiniciar app y Host. El reinicio espera al apagado del Host antes de relanzar Electron y arrancar un Host nuevo; ninguna de las dos acciones recompila los archivos fuente.

`dev:desktop` compila el Host actual, los bundles de cliente, el frontend Web y el shell de Electron, proyecta la CLI compilada y los paquetes del Host privado de Desktop con sus dependencias del espacio de trabajo en un proyecto npm de escritorio desechable, y lanza Electron sin resolver dsh desde npm:

```sh
pnpm run dev:desktop
```

El estado de Harness de desarrollo usa por defecto `apps/desktop/.desktop-build/development/home`, el proyecto npm desechable vive en `apps/desktop/.desktop-build/development/project`, y los datos del navegador de Electron viven en `apps/desktop/.desktop-build/development/electron-user-data`. Las sesiones, la configuración, las credenciales, los enlaces de paquetes y los datos del navegador permanecen así fuera del home normal de Harness del usuario. Un `DSH_HOME` explícito reemplaza solo el home de Harness de desarrollo. Las DevTools del renderer permanecen cerradas por defecto; la depuración de Main, Renderer y el Host dsh escucha en los puertos 9229, 9222 y 9230. `DSH_DESKTOP_MAIN_INSPECT_PORT`, `DSH_DESKTOP_RENDERER_DEBUG_PORT` y `DSH_DESKTOP_HOST_INSPECT_PORT` reemplazan esos puertos, mientras que `DSH_DESKTOP_OPEN_DEVTOOLS=1` abre las herramientas separadas del renderer.

Tras una compilación explícita, `start:desktop` reconstruye el proyecto desechable y lanza los artefactos existentes sin compilar de nuevo:

```sh
pnpm run start:desktop
```

Las contrapartes Web son `pnpm run dev:web` y `pnpm run start:web`, documentadas en la [guía de desarrollo](../../docs/development.es.md). El desarrollo del espacio de trabajo ejecuta los paquetes actuales de la CLI y del Host privado de Desktop bajo Electron RunAsNode. La gestión de plugins y la recuperación usan `$DSH_HOME/profiles/desktop`, separado del runtime desechable del espacio de trabajo. El Host usa la resolución de módulos en runtime tanto en compilaciones de desarrollo como empaquetadas sin crear enlaces de fallback de paquetes oficiales; los paquetes instalados por el desarrollador, incluidos los enlaces, conservan la prioridad nativa. Usar una aplicación desempaquetada para ejercitar Electron RunAsNode, el pnpm incluido, los recursos dsh incluidos y las rutas de instalación y reparación de plugins.

Las [pruebas de teclado nativo y renderer](tests/keyboard.spec.ts) compilan como parte de la verificación de tipos de cliente del repositorio. Sus importaciones de Desktop se limitan a los módulos de entrada, persistencia, IPC, invitados de navegador y overlays libres de Cordis.

### Onboarding de arranque

La entrada de clave de API empieza vacía y usa `autocomplete="new-password"` para pedir a Chromium que no autorrellene las contraseñas de login guardadas.

Los lanzamientos repetidos y `dsh://open` mantienen el espacio de trabajo oculto hasta que la comprobación de credenciales de arranque o una acción de bienvenida permite la entrada. Entrar desde Welcome coloca el foco de teclado en el documento sin seleccionar un control de la barra lateral; la navegación con Tab sigue disponible.

Desktop comprueba las referencias de claves de API de modelos configuradas después de que arranca el Host y antes de abrir el espacio de trabajo. Sin ninguna clave configurada, la ventana de bienvenida ofrece la página de clave de API. Guardar y continuar escribe a través del servicio de credenciales existente usando la referencia configurada del proveedor oficial de DeepSeek, y después abre el espacio de trabajo. Configurar más tarde abre el espacio de trabajo sin guardar el borrador ni un ajuste de finalización; el siguiente lanzamiento del proceso comprueba las credenciales de nuevo. Volver a iniciar sesión regresa a la entrada y limpia la clave no guardada y el mensaje de validación. Los botones conservan sus etiquetas y bloquean las acciones competidoras mientras se guarda o se abre el espacio de trabajo. El marcador del preload de Desktop suprime el diálogo de credenciales de Web, conservando la página de configuración de modelos y el aviso de bienvenida.

La ventana de bienvenida lee el `locale.preference` compartido antes de aparecer. Una elección explícita de inglés o español gana; en caso contrario, Desktop elige el primer idioma del SO soportado y recurre al inglés como fallback. La UI principal lee la misma preferencia y el orden de idiomas del SO a través de su preload aislado antes de montarse. Los cambios de idioma en la configuración actualizan el diccionario y el menú actuales del shell; la selección automática no escribe ninguna preferencia. La ventana de bienvenida no tiene selector de idioma.

La página de espera de login en el navegador ofrece una acción de copiar enlace para la autorización pendiente actual, un indicador de carga y cancelación. Los fallos del portapapeles dejan la acción de copia disponible para reintentar. La retroalimentación de copia se restablece tras dos segundos; el estado copiado deshabilita el enlace hasta que se restablece. El texto de bienvenida usa Montserrat Light con fallbacks del sistema; los botones de acción grandes conservan la fuente del sistema, mientras que los botones de texto usan Montserrat Light. El texto introductorio en inglés es de 24 px en todo. El texto introductorio en español es de 24 px con un nombre de producto de 26 px. Los botones de acción de login tienen 240 px de ancho con etiquetas de 14 px. Los encabezados de estado de autorización usan texto Montserrat Regular de 20 px. La página de clave de API usa un encabezado de 20 px y una acción de retroceso de 14 px, con 84 px entre el borde inferior del botón secundario y el borde inferior de la ventana.

### Apariencia de la ventana de bienvenida

La ventana de bienvenida sigue la apariencia del sistema con los colores claros y oscuros de Platform del diseño y muestra el diseño de entrada de 600 × 700 y el formulario de clave de API, con controles de ventana nativos, un área de título arrastrable, un SVG de marca local, fallbacks sans-serif del sistema y Montserrat Light incluida localmente para el texto que no es de botones. La ventana usa la vitalidad (vibrancy) de menú de macOS o el acrílico de Windows con el tinte de ventana de onboarding: 40 % de blanco en modo claro y 50 % de rgb(24 25 28) en modo oscuro. La entrada React de bienvenida local empaqueta React y el indicador de carga `StateDot` compartido con su CSS; usa el preload aislado sin cargar la aplicación Web principal. La entrada, el estado de inicio de sesión y las páginas de clave de API comparten una fila de acciones fija en la parte inferior; el enlace de volver a iniciar sesión se sitúa debajo. Los botones comparten los tiempos de movimiento de la plataforma, y Reducir movimiento deshabilita sus transiciones. El SO posee la intensidad del desenfoque y las esquinas exteriores. Reducir transparencia de macOS suprime la translucidez, y Aumentar contraste fuerza ese ajuste. Guardar y continuar escribe en el almacén de credenciales de desarrollo; Configurar más tarde abre el espacio de trabajo real sin guardar una clave ni un flag de finalización. [La nota de la ventana](../../.agents/notes/implemented/architecture/2026-09-08-desktop-welcome-window-material.md) posee las decisiones de material y onboarding.

## Empaquetado

<a id="release-versions"></a>

### Versiones de lanzamiento

Antes de cada ejecución de empaquetado de Desktop, confirmar primero la cadena de versión completa con el usuario actual. Comprobar el despliegue seleccionado, la versión base de dsh, los registros de lanzamiento conservados y los objetos publicados, y después proponer la versión exacta para su aprobación. No empezar el empaquetado hasta que el usuario confirme esa versión; el ajuste de despliegue por sí solo no autoriza una elección de versión.

Registrar la versión actual de dsh como base. Un lanzamiento de Desktop de producción usa esa versión exacta, incluidos los identificadores `alpha`, `beta` o `rc`. Un lanzamiento de prueba preserva la base de prelanzamiento completa y añade `.YYYYMMDD.index`; una base estable usa `-test.YYYYMMDD.index` en su lugar.

| Base de dsh | Desktop de producción | Ejemplo de Desktop de prueba |
|---|---|---|
| `0.1.6-alpha.1` | `0.1.6-alpha.1` | `0.1.6-alpha.1.20260916.1` |
| `0.1.6-beta.2` | `0.1.6-beta.2` | `0.1.6-beta.2.20260916.1` |
| `0.1.6-rc.3` | `0.1.6-rc.3` | `0.1.6-rc.3.20260916.1` |
| `0.1.6` | `0.1.6` | `0.1.6-test.20260916.1` |

Usar la fecha real de creación en Asia/Shanghai. Para cada base y fecha, empezar el índice en 1 e incrementarlo tras comprobar los registros de lanzamiento conservados y los objetos publicados; nunca reutilizar una versión publicada. La distribución de prueba no publica la base correspondiente sin sufijo.

Pasar la versión confirmada al comando de empaquetado como `--build-version`, que llega a los nombres de artefactos, al feed de actualizaciones y a la validación de subida como un solo valor. Los manifests conservan la versión del producto, por lo que una compilación de prueba ya no reescribe la familia de lanzamiento y no deja nada que revertir:

```sh
pnpm --dir apps/desktop run package:win:x64 --build-version 0.1.6-alpha.1.20260916.1
```

`--build-version auto` propone el siguiente índice para hoy, leyendo los objetos publicados en el bucket de destino y recurriendo al directorio local de salida de este destino cuando no hay bucket configurado o el listado no puede terminar dentro de su plazo. Confirmar la propuesta que imprime antes de una subida; un script run reenvía `--` por sí mismo, y la entrada de empaquetado lo acepta de ambas formas.

Un lanzamiento de producción publica la versión del producto y no acepta `--build-version`. Al subirlo, se etiqueta el commit empaquetado como `desktop-v<version>` una vez que los artefactos son públicos; una compilación desde un checkout modificado no se etiqueta, y un fallo de etiquetado imprime el comando a ejecutar a mano en lugar de hacer fallar una subida completada. Las compilaciones de prueba y locales se dejan deliberadamente sin etiquetar, y cada artefacto registra `dshBuildCommit` y `dshBuildDirty` en su manifest para que una compilación entregada directamente siga siendo trazable.

La derivación de versiones no cambia el canal de actualización fijo ni los nombres de archivo `nightly.yml` / `nightly-mac.yml`. SemVer ordena `0.1.6-alpha.1 < 0.1.6-alpha.1.20260916.1 < 0.1.6-alpha.2`, y la versión de prueba de una base estable precede a ese lanzamiento estable. Los clientes solo aceptan una versión mayor: reemplazar un feed no puede mover una versión instalada superior a una versión corregida inferior. Esos clientes necesitan instalación manual; mantener el downgrade automático deshabilitado. La [decisión de versiones](../../.agents/notes/implemented/process/2026-09-16-desktop-release-version-derivation.md) explica por qué el canal no aporta el identificador de prelanzamiento.

El empaquetado, la subida y la verificación manual de firmas de macOS leen `apps/desktop/.env.windows`, `.env.macos` o `.env.linux`, seleccionados por plataforma de destino. Copiar la [plantilla de Windows](.env.windows.example), la [plantilla de macOS](.env.macos.example) o la [plantilla de Linux](.env.linux.example) y rellenar los ajustes locales; Git ignora los tres archivos locales, y los artefactos empaquetados los excluyen. Los campos de lanzamiento provienen solo del archivo del destino, sin fallback a variables del sistema o del shell; `PATH`, los proxies y los ajustes de herramientas de compilación permanecen heredados. La versión publicada es un argumento y no un campo de lanzamiento, y la subida la lee del registro de finalización que escribió la ejecución de empaquetado. Los archivos usan UTF-8 con BOM opcional; las rutas relativas de certificado, SignTool, clave de API de Apple y keychain se resuelven desde `apps/desktop`, los valores no se expanden por shell, y las contraseñas que contienen `#` o espacios necesitan comillas. CI también crea el archivo del destino antes de invocar el empaquetado.

Cada comando de empaquetado comprueba el ID de aplicación y, cuando el destino los exige, el origen de actualizaciones y la configuración de firma específica del modo antes de compilar o descargar, y después sondea las herramientas externas que la ejecución usará: el lector de archivos y, en un destino Windows, el compilador del instalador. macOS comprueba la identidad, el Team ID, una estrategia completa de notarización, el archivo p12 local `CSC_LINK` legible, el `CSC_KEY_PASSWORD` explícito y los archivos referenciados de clave de API y keychain; Windows comprueba el certificado público de firma de código, el archivo SignTool, el nombre del contenedor y el formato del PIN. Las compilaciones de Windows de solo preparación y las explícitamente sin firma, y las compilaciones macOS `:dir` sin firma, no requieren credenciales de firma. Las comprobaciones de configuración no autentican el PIN, no inician sesión en el token, no desbloquean un keychain ni contactan con Apple; la firma y notarización reales realizan esas comprobaciones. `--build-version auto` sí contacta con el bucket de destino, incluso bajo `--check`. Ejecutar las mismas comprobaciones por separado:

```sh
pnpm --dir apps/desktop run check:package
```

`prepare:desktop` no es un prerrequisito:

```sh
pnpm run package:desktop
```

La automatización de lanzamientos usa comandos de destino fijos para que la preparación del runtime, la preparación de dsh y electron-builder reciban la misma plataforma y arquitectura:

```sh
pnpm run package:desktop:mac:arm64
pnpm run package:desktop:mac:x64
pnpm run package:desktop:win:x64
pnpm run package:desktop:linux:x64
```

El comando de macOS arm64 requiere Apple Silicon. El comando de macOS x64 se ejecuta en macOS Intel o en Apple Silicon con Rosetta. El comando de Windows x64 requiere Windows x64. El comando de Linux x64 requiere un host Linux x64 y compila el destino local sin firma, sin carril de lanzamiento, artefactos firmados ni publicación.

Cada destino posee sus entradas de paquete empaquetadas, runtime preparado, conjunto de paquetes, árbol dsh, estado de preparación de pnpm, aplicación desempaquetada, metadatos de actualización y artefactos finales bajo `apps/desktop/.desktop-build/targets/<target>/`. La caché de archivos de Electron permanece compartida bajo `.desktop-build/downloads` porque cada nombre de archivo incluye su versión, plataforma y arquitectura y se verifica antes de la extracción. Una compilación de destino nunca consume el estado mutable de preparación de otro destino.

### Selección de archivos de runtime

Desktop empaqueta los paquetes del espacio de trabajo localmente e instala las dependencias externas a través del Node y pnpm incluidos del destino. La [política de archivos de Desktop](scripts/runtime-file-policy.ts) filtra después la copia inmutable `resources/app.asar/dsh/node_modules` antes de la firma y el sellado de integridad. Omite las declaraciones TypeScript, los source maps reconocidos de JavaScript/CSS/TypeScript, las cachés de compilación de TypeScript, el directorio de pruebas de Domino, salidas seleccionadas del compilador nativo y los prebuilds de node-pty de otras plataformas. Preserva el JavaScript de runtime, los módulos nativos y sus helpers DLL/EXE, WASM, los assets desconocidos, las licencias y los avisos. Los manifests de dependencias pasan por la limpieza de metadatos de electron-builder antes del sellado de integridad, por lo que el archivado preserva sus bytes registrados. La política no altera los tarballs de npm, el gestor de paquetes incluido ni los archivos de plugins instalados por el usuario.

El [proveedor de conversión de Office](../../packages/document/office-to-pdf/README.md) transporta el motor nativo declarado del destino, o WASM cuando el kit no declara un destino nativo coincidente. La preparación rechaza un motor de destino ausente antes del empaquetado. Las dependencias completas de Office, incluida la CLI, las bibliotecas JavaScript y los ejecutables, datos, licencias y avisos del motor seleccionado, se desempaquetan bajo `resources/app.asar.unpacked/dsh/node_modules/`. El Host de Desktop resuelve los manifests del motor a estos directorios físicos y aporta a las skills cargadas rutas absolutas del Node independiente y de la CLI desempaquetada. Node vive en `resources/runtime/primary-runtime/dependencies/node/bin/`; la CLI es el `@deepseek-ai/libreoffice-kit/lib/cli.js` desempaquetado. En macOS, el helper nativo recibe el entitlement JIT requerido por el [puente UNO de LibreOffice](https://github.com/LibreOffice/core/blob/master/sysui/desktop/macosx/hardened_runtime.xcent.in).

La aplicación empaquetada ejecuta JavaScript compilado y metadatos Typert pregenerados; no compila plugins TypeScript. La navegación del depurador a nivel de fuente y las declaraciones del editor permanecen disponibles en los paquetes de desarrollo. Las [pruebas de política de copia](tests/runtime-file-policy.spec.ts) cubren las exclusiones y los assets conservados; la [prueba de humo del payload](tests/fixtures/runtime-payload-smoke.mjs) se ejecuta bajo Electron RunAsNode antes de la prueba de humo del Host y la verificación final del inventario. La prueba de humo del payload resuelve el ejecutable ripgrep de la tool de búsqueda y verifica la búsqueda de texto y la enumeración de archivos. Las compilaciones firmadas de Windows ejecutan estas comprobaciones tras la firma de dependencias; las demás compilaciones las ejecutan durante `prepare:dsh`. La [prueba de humo del Host](scripts/smoke-runtime.ts) crea entradas DOCX, XLSX y PPTX con el Python incluido, convierte cada una a través del proveedor real de Office y comprueba la salida PDF. Toda aplicación ensamblada, incluidas las compilaciones de directorio y las de Windows sin firma, repite las comprobaciones de payload y de Host contra el ASAR. Las comprobaciones de integridad de archivos comparan el descriptor archivado completo con la preparación, los bytes de archivos y la membresía en los árboles archivado y desempaquetado, los flags ejecutables registrados para los archivos archivados y los permisos físicos de los archivos desempaquetados. La prueba de humo del Host también obtiene las rutas de la CLI de la skill cargada y ejecuta capacidades y conversión DOCX con un PATH vacío. Los fallos de conversión detienen el empaquetado antes de que se escriba un registro de lanzamiento; las compilaciones DMG/ZIP de macOS ejecutan estas comprobaciones antes de la notarización.

La cualificación de lanzamiento de Windows también ejecuta [comprobaciones de directorio y reemplazo](scripts/smoke-windows.ps1) manualmente tras la compilación de Desktop. Establecer `$Makensis`, `$SevenZip` y `$PluginDir` al compilador NSIS del constructor fijado, al ejecutable de 7-Zip y al directorio de plugins NSIS x86-unicode; pasar el `window-frame.dll` preparado como `-FrameLibrary` para ejercitar también la ruta nativa de extracción y su reporte de fallos. Desde la raíz del repositorio, ejecutar el comando de abajo. Verifica el reemplazo y rollback de directorios y ambos modos de reemplazo de archivos bloqueados; no forma parte del carril de pruebas unitarias.

```powershell
pwsh -NoProfile -File apps/desktop/scripts/smoke-windows.ps1 -Makensis $Makensis -SevenZip $SevenZip -PluginDir $PluginDir -FrameLibrary apps/desktop/.desktop-build/targets/win-x64/installer-ui/window-frame.dll
```

El instalador de Windows comprueba si hay una aplicación en ejecución al arrancar y tras la selección del destino, antes de extraer la nueva versión junto al directorio de instalación. Lo comprueba de nuevo antes de reemplazar directorios mediante renombrados en el mismo volumen. Una aplicación en ejecución bloquea la instalación; los lanzamientos de actualización le conceden hasta diez segundos para salir. Las actualizaciones en la misma ruta preservan el directorio antiguo hasta que la promoción tiene éxito; un fallo de extracción lo deja intacto, y un fallo de promoción intenta restaurarlo. El instalador elimina el respaldo antiguo antes del lanzamiento. Una terminación forzada o un corte de energía pueden dejar directorios `.new-*` o `.old-*`; las migraciones de ubicación de instalación y de ámbito conservan el flujo de desinstalador antiguo de electron-builder.

Cuando la extracción falla, el instalador escribe un reporte con el resultado de 7-Zip y su salida de error completa en el directorio de caché del actualizador como `%LOCALAPPDATA%\<package-derived name>-updater\installer-logs\extract-failure-<timestamp>.log` (actualmente `@deepseek-aidsh-desktop-updater`) y muestra la primera línea de error con un botón **Copiar detalles del error**; las instalaciones silenciosas solo escriben el reporte. Las compilaciones de Windows sin firma (`DSH_DESKTOP_UNSIGNED=1`) nombran su instalador `deepseek-harness-<version>-win-x64-unsigned.exe` para que no puedan confundirse con artefactos de lanzamiento.

<a id="upload-updates"></a>

### Subida de actualizaciones

Las descargas fijas del instalador usan `pnpm run upload:latest:mac:arm64`, `pnpm run upload:latest:mac:x64` o `pnpm run upload:latest:win:x64` desde la raíz del repositorio. Suben el DMG o EXE del destino completado a `desktop/dsh-latest-macos-arm64.dmg`, `desktop/dsh-latest-macos-x64.dmg` o `desktop/dsh-latest-windows-x64.exe`. Las URL de producción empiezan por `https://download.deepseek.com/`; las URL de prueba usan `DOWNLOAD_TEST_ORIGIN`. Ambos despliegues reutilizan el despliegue, bucket y credenciales del dotenv del destino, toda la validación normal de lanzamiento y la auditoría de subida de abajo. Cada comando reemplaza un objeto fijo sin publicar feeds, blockmaps ni etiquetas de lanzamiento. Las descargas fijas de prueba se comparten entre IDs de lanzamiento en el bucket de prueba; la URL de actualización empaquetada sigue requiriendo su ID de lanzamiento original. La publicación es explícita, incluidas las versiones de prelanzamiento. La infraestructura de despliegue debe configurar la revalidación o purgar las descargas fijas en caché tras el reemplazo. Las pruebas locales de loopback cubren la subida; los operadores de lanzamiento poseen la aceptación real de COS y CDN.

Las subidas de prueba y producción a través de `upload:*` conservan un directorio nuevo `.desktop-build/upload-records/<environment>-<target>-*` tras el preflight de lanzamiento. `plan.json` registra el destino, la versión, el tamaño y SHA-512 de cada archivo y los bytes YAML publicados; el `events.jsonl` volcado registra la intención de PUT y el estado de respuesta y ID de solicitud disponible; `result.json` registra la finalización o la última fase fallida. Un resultado final ausente significa interrupción o almacenamiento no disponible, no éxito. No se registran valores de credenciales, cabeceras de autorización ni errores crudos del SDK. Los fallos de escritura de auditoría detienen los PUT posteriores. Cada objeto es un PUT de Tencent COS en stream con longitud explícita y Content-MD5; el SDK de COS repite una solicitud solo cuando su cuerpo no es un stream, y este subidor tampoco reintenta. Conservar los registros parciales e inspeccionar el estado remoto antes de otra operación: un timeout o una escritura de recibo fallida no prueban que el objeto no se almacenó. Estos registros son locales, no a prueba de manipulaciones ni respaldados automáticamente; archivar los registros de cada lanzamiento con su evidencia de compilación en almacenamiento controlado. La relectura por CDN pública permanece como cualificación de lanzamiento separada, marcada explícitamente `not-performed` en el resultado de la subida.

Los operadores de Windows pueden conservar un objeto CLIXML con campos SecureString `SecretId` y `SecretKey` cifrados con DPAPI fuera del repositorio. El [lanzador de credenciales](scripts/upload-with-credentials.ps1) requiere un `-CredentialFile` explícito y `-Environment production` o `test`; sin `-Upload`, solo verifica el descifrado y la inyección en un hijo Node local, sin ninguna solicitud de red. Requiere Node en `PATH` y el usuario y la máquina de Windows que cifraron el archivo. Los campos en texto plano, vacíos o de solo espacios fallan. El entorno padre no cambia; el hijo recibe solo el par de COS seleccionado tras eliminar los secretos no relacionados y las opciones de precarga de Node. El stderr crudo del hijo se suprime y los valores de credenciales en stdout se redactan. Esta comprobación no prueba la autorización COS. Una subida explícita requiere además `-Upload -Target <target> -Bucket <bucket>` y los prerrequisitos normales de lanzamiento completado de abajo; la subida real a la nube permanece como cualificación del operador de lanzamiento. Añadir `-Latest` a esa invocación de subida para reemplazar el instalador fijo sin publicar feeds de actualización ni una etiqueta de lanzamiento. Este lanzador soporta claves permanentes, no credenciales STS. Una subida explícita requiere que el despliegue y el bucket seleccionados coincidan con el dotenv del destino y el registro de paquete completado antes de las escrituras de red; usa el par de credenciales DPAPI aunque el dotenv contenga otras claves COS.

`DSH_DESKTOP_AUTO_UPDATE_ENV` selecciona `test` o `production` tanto para la URL incrustada durante el empaquetado como para la subida COS posterior; un valor ausente selecciona `test`. El empaquetado de prueba requiere su origen HTTPS en `DOWNLOAD_TEST_ORIGIN`; producción usa `https://download.deepseek.com`. La subida requiere el bucket seleccionado en `DOWNLOAD_TEST_COS_BUCKET` o `DOWNLOAD_PROD_COS_BUCKET`. Los feeds de producción usan `dsh-desk/feeds/<target>/` y los binarios usan `dsh-desk/bin/<target>/`. Los lanzamientos de prueba requieren `DOWNLOAD_TEST_RELEASE_ID`: 32 caracteres hexadecimales en minúsculas insertados como `dsh-desk/<release-id>/feeds/<target>/` y `dsh-desk/<release-id>/bin/<target>/`. Las referencias YAML, los alias de canal estable y los blockmaps permanecen dentro de ese directorio de lanzamiento. Los destinos son `mac-arm64`, `mac-x64` y `win-x64`.

El destino de actualización y las credenciales de subida siguen al despliegue seleccionado:

| Entorno | Origen público | Bucket COS | Credenciales COS |
|---|---|---|---|
| `test` o sin definir | `DOWNLOAD_TEST_ORIGIN` | `DOWNLOAD_TEST_COS_BUCKET` | `DOWNLOAD_TEST_COS_SECRET_ID`, `DOWNLOAD_TEST_COS_SECRET_KEY` |
| `production` | `https://download.deepseek.com` | `DOWNLOAD_PROD_COS_BUCKET` | `DOWNLOAD_PROD_COS_SECRET_ID`, `DOWNLOAD_PROD_COS_SECRET_KEY` |

Generar un ID nuevo para cada lote de lanzamientos de prueba con el comando de abajo y copiar su salida en `DOWNLOAD_TEST_RELEASE_ID` en `.env.macos` o `.env.windows`. Estos archivos de plataforma ignorados por Git poseen el valor; las variables de shell no lo anulan, y los valores dotenv no se expanden por shell. Conservar el ID durante el empaquetado, la subida y los reintentos; la subida rechaza un registro de finalización con una URL de actualización distinta. Para probar una actualización entre versiones, reutilizar el ID del cliente instalado para la versión posterior. Producción no usa este campo.

```sh
node --input-type=module -e "import { randomBytes } from 'node:crypto'; console.log(randomBytes(16).toString('hex'))"
```

Distribuir cada lote de prueba a través de sus enlaces de descarga completos. Los clientes de prueba instalados conservan el feed de su lote y no descubren un ID nuevo automáticamente. La validación de formato no puede establecer la aleatoriedad; usar la salida del generador. Las rutas aleatorias reducen las adivinanzas, no el acceso por parte de quienes poseen el enlace; retirar un lote requiere eliminar sus objetos COS y purgar su directorio CDN.

Configurar el origen de actualización y el bucket COS seleccionado, SecretId y SecretKey en el archivo dotenv del destino, y después empaquetar y subir el mismo destino:

```sh
pnpm run package:desktop:mac:arm64
pnpm run upload:mac:arm64
```

El archivo dotenv del destino para el empaquetado de prueba interna establece explícitamente `DSH_DESKTOP_AUTO_UPDATE_ENV=test` y `DOWNLOAD_TEST_ORIGIN=https://download-test.deepseek.com`; las subidas usan `DOWNLOAD_TEST_COS_BUCKET=bj-toc-download-test-1320056602` y credenciales de prueba separadas. Tanto prueba como producción usan el canal Nightly fijo; la selección de despliegue no habilita el cambio de canal.

Los paquetes de prueba interna temprana usan el despliegue `test`. Seleccionar `production` explícitamente solo para un lanzamiento de producción; cambiar las credenciales de subida no reorienta un paquete existente. El empaquetado no requiere credenciales COS, deshabilita la publicación de electron-builder, despoja las credenciales COS de los procesos hijo y registra la finalización solo después de que la firma y la notarización tienen éxito. La subida valida este registro, el despliegue, el destino, la versión compartida, los nombres de archivo, los tamaños y el SHA-512 antes de leer las credenciales. Los paquetes y blockmaps se suben antes que el YAML; los objetos históricos se conservan. Cada lanzamiento publica `nightly.yml` o `nightly-mac.yml`; los lanzamientos estables también publican `latest.yml` o `latest-mac.yml` apuntando a los mismos artefactos. El YAML publicado usa URL absolutas de binarios. El subidor deja Cache-Control sin definir, incluida la cabecera vacía que el SDK de COS añadiría de otro modo: la infraestructura de despliegue posee la política de caché, con feeds sin caché y caché de binarios configurable por separado. Serializar la publicación por destino y verificar los artefactos públicos y el contenido del feed antes de la cualificación del lanzamiento.

La configuración de macOS usa el entorno de lanzamiento requerido en lugar de aceptar el primer certificado que aparezca en un keychain. Rechaza valores vacíos, un Team ID malformado, una identidad de firma que incluya el prefijo `Developer ID Application:` que electron-builder no soporta, y credenciales de notarización incompletas. El empaquetado de macOS requiere la identidad configurada y su clave privada. La preparación del runtime aplica esa identidad, una marca de tiempo segura y el hardened runtime a cada archivo Mach-O incrustado; tras firmar la aplicación, una comprobación estricta profunda rechaza cualquier otra autoridad hoja o Team ID antes de la creación de artefactos. Los comandos del instalador de macOS de destino fijo crean copias separadas de la aplicación firmada y ejecutan dos carriles de artefactos concurrentemente. Un carril notariza y grapa la app antes de generar el ZIP y sus metadatos de actualización. El otro encierra su copia firmada de la app en un DMG firmado, y después notariza, grapa y verifica el DMG; su app interior no tiene ticket grapado individualmente. Ambos carriles deben terminar con éxito antes de que sus artefactos lleguen al directorio final y se escriba el registro de finalización del lanzamiento. Los comandos firmados de solo directorio también requieren credenciales de notarización y esperan a la notarización de Apple y al grapado de la app; los comandos macOS `:dir` sin firma omiten por completo credenciales, firma y notarización. La [decisión de notarización paralela](../../.agents/notes/implemented/process/2026-09-09-parallel-macos-notarization.md) posee el aislamiento de copias y la semántica de tickets de contenedores. `CSC_LINK` debe nombrar un p12 local que contenga el certificado Developer ID Application y la clave privada; las URL y las entradas Base64 no están soportadas. `CSC_KEY_PASSWORD` es su contraseña de exportación, no una contraseña de cuenta de Apple ni de login; un valor explícitamente vacío soporta un p12 sin cifrar. Antes de compilar, el empaquetado crea y desbloquea un keychain temporal privado, importa el p12, autoriza la firma y firma una pequeña sonda. La firma del runtime y de la app usa este keychain explícitamente; los keychains de login existentes no requieren preparación ni desbloqueo manual. Los procesos hijo reciben su ruta sin la contraseña del p12. El keychain se elimina tras el éxito o el fallo ordinario; CI debe limpiar las credenciales temporales tras una terminación forzada. CI escribe el certificado y `.env.macos` desde su almacén de secretos, restringe el acceso a los archivos y elimina ambos tras el job. El `CSC_NAME` ambiental y el orden de descubrimiento de certificados no seleccionan al propietario del lanzamiento. Las credenciales de notarización pueden usar en su lugar la estrategia completa de Apple ID o de perfil de keychain de electron-builder. Las dos variables de identidad de macOS también son necesarias al repetir la comprobación de la aplicación manualmente con `pnpm --dir apps/desktop run verify:mac-signature -- <path-to-app>`.

La firma de macOS visita los archivos reales sin seguir los alias symlink de Frameworks. Los recursos PAK conservan todos los idiomas distribuidos y quedan sellados por la firma del Framework o aplicación que los envuelve en lugar de recibir firmas individuales. La [política de lanzamiento](../../.agents/notes/implemented/architecture/2026-08-25-electron-desktop-packaging-and-updates.md) posee el parche de dependencias y los requisitos de verificación.

La preparación del runtime de macOS cachea las firmas Mach-O verificadas de una sola arquitectura en `.desktop-build/targets/<target>/signature-cache`. Las claves incluyen los bytes y permisos de entrada, el certificado hoja real de la sonda de firma, el identificador, los bytes de entitlements, la versión de macOS y las herramientas y política de firma. Los commits de Git no determinan la reutilización: los cambios de bytes no confirmados invalidan el archivo afectado. Cada acierto verifica los bytes cacheados, la firma estricta, el certificado, el identificador, los entitlements, la marca de tiempo segura y el hardened runtime antes de reemplazar una entrada sin cambios. Los binarios universales se firman cada vez. La integridad del runtime y las pruebas de humo, la firma de la app y la notarización de Apple se siguen ejecutando. La caché requiere almacenamiento de compilación local confiable. La corrupción de la caché o los enlaces inseguros hacen fallar la compilación; detener el empaquetado antes de eliminar el directorio de caché afectado y reintentar. Las etapas de firma con éxito podan las entradas completas a un presupuesto de payload de un GiB; las entradas temporales interrumpidas requieren eliminación manual. La expulsión concurrente puede hacer fallar a un lector de forma segura. Los logs reportan los recuentos de aciertos, fallos y no cacheados.

Los comandos de empaquetado de Mac imprimen `DESKTOP_PACKAGING_RECORD` con un directorio único bajo `apps/desktop/.desktop-build/packaging-runs/`. Tras leer la configuración local, cada ejecución conserva `run.json` (versión publicada, versión del producto, commit de Git, flag de worktree sucio, destino y versión de Node), `events.jsonl` (fases con marca de tiempo, duraciones, atribución de salida paralela y restauración de proxy), `stdout.log` / `stderr.log` del hijo redactados, y `result.json` (resultado global, resultados por fase y directorio de artefactos). Los eventos también registran la concurrencia de empaquetado y si cada proxy está configurado. Los logs sobreviven a los fallos y a las compilaciones posteriores; no hay eliminación automática. Un `result.json` ausente significa que la finalización no está confirmada. Los valores de credenciales conocidos se redactan; los entornos y los argumentos de autenticación de notarytool no se registran. La preparación del runtime registra por separado la preparación de paquetes, la instalación, la materialización, la firma, los manifests, las pruebas de humo, la verificación del descriptor y la limpieza. Las duraciones de fases anidadas se solapan y no deben sumarse.

La notarización de la app y del DMG registra cada una un ID de envío y duraciones separadas `notarytool:upload:*` y `notarytool:wait:*`. La subida usa `submit --no-wait` e incluye la autenticación, la validación local, la transferencia y la aceptación del servidor; no es tiempo puro de transferencia. La espera empieza después de que ese comando regresa e incluye el sondeo y el procesamiento restante de Apple; Apple puede empezar a procesar antes de que regrese el envío de la subida. Los logs de estado y diagnóstico de Apple se conservan, incluido el rechazo; las comprobaciones de firma, las comprobaciones de aceptación y el grapado siguen siendo propiedad de `@electron/notarize`. Los comandos firmados de paquete de solo directorio usan esta misma ruta medida de notarización de la app. La salida individual de subprocesos permanece en vivo en la terminal, mientras que los fallos de fase y los errores anidados se conservan en el journal. Ambas plataformas registran los fallos de empaquetado del proceso padre e imprimen diagnósticos redactados, incluidas las instrucciones de recuperación del proxy, en la terminal. El comando `check:package` de solo configuración no crea ningún log de ejecución.

El empaquetado de Mac lee tres campos de ajuste de `.env.macos`:

| Ajuste | Por defecto | Ámbito |
|---|---|---|
| `DSH_DESKTOP_MACOS_PACK_CONCURRENCY` | `4` | Workers para los tarballs del espacio de trabajo propios y del proveedor; requiere un entero positivo. |
| `DSH_DESKTOP_MACOS_DOWNLOAD_PROXY` | Vacío | Origen de proxy HTTP/HTTPS para Electron, assets de runtime, instalación de pnpm y descargas del constructor. |
| `DSH_DESKTOP_MACOS_NOTARIZATION_PROXY` | Vacío | Origen de proxy HTTP para las herramientas de Apple a través de ajustes temporales de proxy del sistema. |

Los campos de proxy son independientes y rechazan credenciales en URL, rutas, queries y fragmentos. Los valores vacíos preservan la red heredada. Un proxy de descarga explícito reemplaza las variables de proxy de los procesos hijo y solo omite los hosts locales; no cambia los ajustes del sistema. Windows y el `release:pack` independiente conservan sus valores de concurrencia existentes. Las direcciones de proxy de la empresa pertenecen al archivo local ignorado; ver la documentación interna para las direcciones.

Las herramientas de Apple usan los proxies HTTP/HTTPS del servicio de red de macOS activo. El enrutado de notarización configurado comprueba la alcanzabilidad del proxy, guarda los ajustes de ese servicio, habilita el proxy alrededor de ambos carriles de artefactos y restaura los ajustes guardados después de que ambos carriles se asientan. Un proxy originalmente deshabilitado con servidor vacío y puerto cero se restaura deshabilitándolo; el servidor y el puerto temporales pueden quedar almacenados pero inactivos. Las compilaciones de solo directorio lo aplican a la notarización de la app tras la compilación firmada de directorio. Esto afecta temporalmente a otras aplicaciones y requiere permiso para cambiar los proxies del sistema; las configuraciones PAC, de autodescubrimiento, SOCKS y de proxy autenticado deben deshabilitarse primero. El empaquetado y la recuperación adquieren el mismo bloqueo de archivo POSIX por usuario antes de leer los datos de recuperación o cambiar los proxies; la salida del proceso libera la propiedad, mientras que el archivo de bloqueo permanece en su sitio. El bloqueo carga `@deepseek-ai/node-addon-system/flock` en el primer uso en lugar de al arrancar el script, por lo que `check:package` y la entrada de empaquetado cargan en un checkout que no ha compilado `native/system`; cuando el binario del addon del host o el JavaScript de la entrada falta en el momento del bloqueo, el loader ejecuta `pnpm run build:native-system` y `pnpm --dir native/system run build:ts` antes de bloquear, de modo que la recuperación también funciona en ese checkout. Esto evita transacciones de proxy solapadas entre checkouts; otros usuarios y herramientas de ajustes de red no deben cambiar estos ajustes concurrentemente. SIGINT/SIGTERM esperan al trabajo activo antes de la restauración. Tras una terminación forzada o un error de restauración, detener los procesos de notarización restantes y ejecutar `pnpm --dir apps/desktop run restore:mac-proxy`; el registro guardado permanece hasta que la restauración tiene éxito. Las comprobaciones de configuración validan la sintaxis de la URL sin cambiar los ajustes del sistema ni contactar con el proxy.


El comando requiere `DSH_DESKTOP_APP_ID` y las dependencias normales de compilación, incluidos Python y las herramientas de compilación de Visual C++ para los módulos nativos. Establecer `PYTHON` al ejecutable de Python cuando esté ausente de `PATH`. ### Interfaz del instalador de Windows

El instalador de Windows usa páginas NSIS nativas con paletas clara y oscura, sombras del sistema, un directorio de instalación editable y una página final cuya casilla de lanzamiento está seleccionada por defecto. La instalación está restringida al usuario actual. Hacer clic en Instalar o pulsar Enter valida la ruta actual; los destinos nuevos deben estar vacíos, y los destinos no vacíos deben ser instalaciones registradas. Los ejecutables en ejecución en la ruta de instalación afectada producen un aviso nativo y siguen en ejecución; las aplicaciones con el mismo nombre en otros directorios no bloquean la instalación. Las actualizaciones silenciosas esperan hasta diez segundos a que la aplicación afectada salga, y después se detienen con código de salida 2 si sigue en ejecución.

El tema sigue a Windows al arrancar; `/THEME=light`, `/THEME=dark` y `/THEME=auto` seleccionan una paleta explícitamente. La ventana aparece después de que sus controles de marca están listos. Cuando la página de bienvenida aparece por primera vez, el instalador se eleva sobre las ventanas ordinarias una vez y hace parpadear su botón de la barra de tareas si otra ventana tiene el foco; no permanece siempre encima. El progreso lee el porcentaje del extractor 7-Zip fijado; la promoción de directorios, el registro y la limpieza conservan estimaciones acotadas. El porcentaje ponderado no predice el tiempo restante. Después de que NSIS reporta éxito, la barra se llena en 600 ms y muestra el 100 % brevemente antes de que aparezca la página final; la transición apunta a 750 ms. La página final preserva la posición de la ventana. Finalizar descarta el instalador antes de lanzar el ejecutable instalado; un fallo de lanzamiento restaura la página para reintentar. El reemplazo de directorios y la recuperación de fallos siguen el flujo de instalación descrito arriba. La preparación del perfil del primer lanzamiento sigue siendo una operación de Desktop separada.

El empaquetado de Windows compila un helper Win32/GDI+ x86 con Visual C++ Build Tools y un SDK de Windows; las compilaciones firmadas firman este helper a través del firmante de Windows configurado. El hook de preparación deja la recolección de dependencias de producción a electron-builder en cada plataforma. La [decisión del instalador](../../.agents/notes/implemented/architecture/2026-09-10-windows-native-installer-pages.md) registra la integración NSIS y las comprobaciones de lanzamiento.

Ejecutar `pnpm --dir apps/desktop run test:installer` desde la raíz del repositorio en un escritorio Windows x64 interactivo para compilar y ejercitar un pequeño payload de prueba nativo a través de la configuración del instalador de producción. Cada ejecución usa una identidad de producto única y ejercita secuencialmente las variantes del instalador solo en inglés y solo en español, seleccionando las etiquetas de prueba a partir del botón de bienvenida mostrado. Ambas variantes se instalan en directorios privados y se desinstalan tras las pruebas; las capturas de pantalla y los resultados permanecen bajo `.desktop-build/installer-tests/`. Las comprobaciones incluyen actualizaciones a rutas registradas con separadores finales y el rechazo de raíces de unidad. El flag opcional `--signed` usa la configuración EV de Windows de abajo para firmar los ejecutables de prueba y el helper antes de incrustarlos; no habilita un feed de actualización.

El desinstalador de Windows elimina el directorio de datos de usuario de Electron (almacenamiento y cachés del navegador bajo `%APPDATA%`, anidado bajo el ámbito del paquete), el directorio de producto de `%APPDATA%` y la caché de descargas del actualizador bajo `%LOCALAPPDATA%` junto con la aplicación, y después elimina los directorios ordinarios vacíos de ámbito bajo `%APPDATA%`. El home de Harness (`~/.dsh` o `DSH_HOME`: sesiones, configuración, credenciales, plugins) nunca se toca, y un `DSH_HOME` publicado como variable de entorno de Windows protege además cualquier destino que se solape con él. Las desinstalaciones silenciosas eliminan los mismos datos; un desinstalador iniciado con `--updated` o `/KEEP_APP_DATA`, como hace electron-builder para las actualizaciones en el lugar y para reemplazar una instalación más antigua desde otro directorio, los conserva. La eliminación se ejecuta a través del helper nativo, que rechaza las carpetas protegidas de Windows y las rutas que se solapan con la instalación o el home, requiere una unidad local fija, deja en su sitio una raíz o ancestro enlazado, desenlaza los puntos de reanálisis sin entrar en sus destinos, limpia los atributos de solo lectura y sigue eliminando hermanos tras un archivo bloqueado; el residuo nunca detiene la desinstalación ni se reporta. La instalación registra `InstallLocation` en la entrada de desinstalación de Windows como metadato de inventario estándar; en Windows 11, Desinstalar en el menú contextual del menú Inicio abre la lista de aplicaciones instaladas para cada aplicación Win32, y solo los paquetes MSIX se desinstalan directamente desde ahí. El desinstalador declara reconocimiento de DPI y usa Segoe UI. Este comportamiento es exclusivo de Windows.

Usar `node apps/desktop/scripts/test-windows-installer.mjs --uninstall-only --compile-only` para compilar fixtures aislados en inglés y español con un nombre de paquete de ámbito por ejecución. Omitir `--compile-only` para ejecutar la regresión del eliminador nativo y las comprobaciones interactivas, silenciosas, `--updated`, `/KEEP_APP_DATA` y `DSH_HOME`-dentro-de-datos-de-Electron contra datos sembrados. La compilación no establece el comportamiento de desinstalación instalada.

### Firma EV de Windows

La firma del runtime comparte archivos firmados completos entre los worktrees de la cuenta de Windows actual. `DSH_DESKTOP_WINDOWS_SIGNATURE_CACHE_DIR` en `.env.windows` selecciona un directorio absoluto de unidad fija; el valor por defecto es `%USERPROFILE%\.dsh-desktop-signing\signature-cache\v1`. Los directorios de caché deben pertenecer a la cuenta actual y excluir a las demás cuentas ordinarias de sus permisos de acceso; las rutas enlazadas se rechazan. Las entradas identifican los bytes originales, el certificado público y la cadena de herramientas de firma. Cada restauración comprueba el digest, la confianza de Windows, la marca de tiempo y el certificado antes de reemplazar el archivo sin firmar; las entradas inválidas detienen el empaquetado sin fallback hardware. La antigüedad de la caché por sí sola no dispara la firma. La caché confía en los programas que se ejecutan como la misma cuenta y no se defiende de los administradores. La [decisión de la caché de firmas del runtime](../../.agents/notes/implemented/process/2026-09-17-windows-runtime-signature-cache.md) posee la cualificación y los límites de diseño.

El preflight, la firma del runtime primario, la firma del runtime de la aplicación y la creación de artefactos mantienen cada uno el bloqueo de etapa de firma de la cuenta hasta que sus procesos hijo supervisados se asientan. Otras compilaciones esperan antes de entrar en esas etapas; la compilación y la preparación no mantienen el bloqueo. Los workers de firma del runtime poseen sus bloqueos, por lo que terminar solo el proceso de empaquetado exterior no desbloquea un usuario de caché superviviente. La migración y el mantenimiento adquieren el mismo bloqueo; los comandos de firma más antiguos o externos no participan y deben programarse por separado. La espera de etapa está fuera del plazo del preflight. Cerrar el identificador de etapa libera la contención ordinaria sin eliminar el enclavamiento de intento hardware separado; un fallo hardware retenido sigue requiriendo recuperación por el operador.

La copia de aciertos de caché, el hashing y las comprobaciones de confianza por archivo se ejecutan con los workers de `DSH_DESKTOP_WINDOWS_SIGNATURE_CACHE_CONCURRENCY` de `.env.windows` (por defecto `4`, entero `1`–`8`). Todas las restauraciones y su postverificación terminan antes de que los fallos de caché entren en la firma hardware serial. Un fallo de restauración o verificación detiene el nuevo despacho y drena el trabajo activo antes de liberar el bloqueo de etapa; la firma hardware, las pruebas de humo del runtime y la validación final de integridad siguen siendo necesarias.

Cada etapa del runtime escribe `SIGNATURE_CACHE_SUMMARY` en stdout y en su journal de empaquetado, incluidos el directorio real, la identidad de la política, los recuentos de aciertos y fallos, las entradas recién publicadas y conservadas, las solicitudes de firma, las solicitudes de firma evitadas y los fallos de validación. Los tiempos distinguen la firma, la verificación de confianza de los archivos restaurados y recién firmados, y la restauración; la restauración incluye su comprobación de confianza y la limpieza de la preparación. Estos contadores excluyen el preflight, la firma final de artefactos y las comprobaciones exteriores de firma del runtime. Los eventos del bloqueo de etapa registran la espera por separado. Los tiempos concurrentes suman trabajo por archivo en lugar de tiempo de etapa de reloj.

Usar `pnpm --dir apps/desktop run cache:windows-signatures --usage` para inspeccionar bytes y recuentos de entradas estructuralmente completas, o `--from <absolute-old-cache>` para importar una caché explícitamente seleccionada propiedad de la misma cuenta. La migración deja la fuente sin cambios, omite los nombres de preparación, rechaza las entradas corruptas y conserva las entradas existentes válidas incluso cuando sus bytes de marca de tiempo difieren. `--clear` elimina explícitamente las entradas completas bajo el bloqueo de etapa; no se ejecuta ninguna expulsión automática por capacidad. `--directory <absolute-cache>` selecciona un destino de mantenimiento sin cargar credenciales de lanzamiento. Las entradas de preparación incompletas permanecen intactas y se cuentan por separado; inspeccionarlas solo después de que todas las compilaciones se hayan detenido. Estos comandos nunca limpian la evidencia de fallos hardware. El almacenamiento por defecto está fuera de AppData para que la virtualización del lanzador MSIX no divida la caché de la cuenta; los overrides redirigidos fallan explícitamente.

Las compilaciones firmadas de Windows ejecutan un preflight de firma supervisado antes de la compilación o la preparación de dependencias. La configuración estática, la validez del certificado, el almacenamiento de auditoría, la disponibilidad del compilador y cualquier enclavamiento de firma retenido se comprueban sin acceso al token. El compilador C# local de .NET Framework crea una pequeña sonda privada; el firmante de producción la firma una vez, y la verificación requiere el certificado configurado y una marca de tiempo antes de que la compilación continúe. La sonda nunca se ejecuta. El plazo global de 60 segundos del preflight incluye los intentos de marca de tiempo; la expiración del plazo, los errores de firma hardware y los fallos de verificación detienen la ejecución sin otro intento hardware. El éxito prueba que la ruta de firma actual funciona, no que el PIN se autenticó de forma independiente: SafeNet puede reutilizar el estado de login. No cerrar sesión ni repetir la autenticación para probar el PIN. Los modos `--check`, de solo preparación y `--unsigned` no ejecutan este preflight hardware; los artefactos sin firma siguen siendo inelegibles para la subida de lanzamiento. Las pruebas de regresión automatizadas usan un firmante falso; los operadores de lanzamiento cualifican el hardware real por separado.

Las subidas NSIS de Windows requieren el `.exe.blockmap` generado y no vacío junto al instalador. El blockmap se sube antes que el YAML del canal; los metadatos del instalador NSIS no requieren el `blockMapSize` incrustado que usa el formato separado de instalador web. Las pruebas del plan de archivos usan el generador de blockmaps del constructor fijado, no un campo de mapa incrustado escrito a mano.

La configuración firmada de Windows deriva el `publisherName` del actualizador de los atributos `CN`, `O` y `C` del mismo certificado público. Cada uno debe estar presente, no vacío y con un solo valor. Estos atributos de identidad permiten la renovación del certificado sin fijar una huella de certificado hoja. El `app-update.yml` de la aplicación instalada lleva el editor esperado; el feed descargado no lo elige. Las compilaciones de prueba sin firma omiten la configuración del actualizador. Ver el [registro de cualificación de firmas](tests/README.es.md) para la verificación con archivos reales y sus límites.

Para el token SafeNet de este proyecto, `SignTool Error: No private key is available.` indica un PIN incorrecto. Detener todos los intentos de firma inmediatamente y esperar a que el usuario corrija el PIN antes de continuar. Cinco intentos de PIN incorrectos bloquean el token. No reintentar el empaquetado ni las sondas de firma tras este error. El firmante serializa las operaciones del token y rechaza todas las tareas en cola tras el primer fallo.

Los comandos de paquete de Windows imprimen `DESKTOP_PACKAGING_RECORD` con un directorio único bajo `.desktop-build/packaging-runs/`. Cada ejecución conserva `run.json`, `events.jsonl` con marcas de tiempo, `stdout.log` y `stderr.log` redactados, y `result.json`. Un fallo de firma también escribe `fatal.json` y notifica al padre a través de stderr; el supervisor solicita inmediatamente la terminación de su árbol de procesos de etapa y espera la salida. Las etapas fallidas no pueden iniciar etapas posteriores ni crear un registro de finalización de lanzamiento. Los fallos del journal también detienen la ejecución. Los errores de terminación siguen siendo fallos y requieren inspección del operador; un registro final ausente significa que la finalización no se estableció.

La firma hardware requiere una ejecución supervisada. Antes de invocar el intérprete de comandos, el firmante adquiere atómicamente `%USERPROFILE%/.dsh-desktop-signing/attempt.json` y registra el intento. Solo una firma con éxito seguida de la verificación de la firma primaria configurada libera ese archivo; las marcas de tiempo se completan después sin acceso hardware. Un fallo, una interrupción, un enclavamiento existente o un almacenamiento de auditoría no disponible impide cualquier acceso hardware posterior, incluido desde otra instancia del firmante, proceso o checkout bajo la misma cuenta de Windows. No hay recuperación temporizada ni reintento automático. Un administrador debe inspeccionar la evidencia retenida y el estado del token antes de autorizar explícitamente la recuperación del enclavamiento; iniciar sesión en el token o reemplazar un archivo de PIN no lo limpia. Los registros distinguen la intención de firma, el PID del intérprete de comandos y la finalización; no miden los intentos internos de autenticación CSP/token. Los argumentos de comandos, los PIN y los entornos de credenciales no se registran. Las cuentas de Windows independientes y los programas de firma no relacionados quedan fuera de este enclavamiento.

El empaquetado de Windows fija el filtro de 7-Zip a `BCJ` por compatibilidad con el decodificador NSIS incluido. Esto preserva los binarios ARM64 transportados por las dependencias en los instaladores x64; el filtrado automático de ARM64 produce entradas que este decodificador no puede extraer.

NSIS elimina su árbol temporal de extracción durante la instalación, antes de la página de finalización o de un lanzamiento automático. Los paquetes de producción instalados permanecen como archivos ordinarios; el arranque no los extrae de nuevo. La instalación sigue escribiendo el árbol completo de la aplicación.

Rellenar `.env.windows` con `DSH_DESKTOP_WINDOWS_CER_FILE` (certificado público hoja EV), `DSH_DESKTOP_WINDOWS_SIGNTOOL` (SignTool compatible con SafeNet), `DSH_DESKTOP_WINDOWS_KEY_CONTAINER` (contenedor de clave privada correspondiente) y `DSH_DESKTOP_WINDOWS_TOKEN_PIN` (contraseña del token). La clave privada permanece en el token USB; mantener el certificado y el archivo local de credenciales fuera de Git.

```sh
pnpm run package:desktop:win:x64
```

Insertar y desbloquear el token antes del empaquetado. El hook de electron-builder pasa cada artefacto al `scripts/windows-sign.cmd` CRLF, que invoca el SignTool configurado una vez con `/f`, SafeNet `/kc "[{{PIN}}]=container"`, `/csp "eToken Base Cryptographic Provider"`, un digest de archivo SHA-256, sin marca de tiempo. El hook completa después una marca de tiempo DigiCert SHA-256 RFC 3161 en copias aisladas sin credenciales de firma. El hook nunca sustituye el SignTool incluido de electron-builder y nunca reintenta una solicitud de firma fallida. El empaquetado de lanzamiento de Windows falla en lugar de emitir artefactos sin firmar cuando el SignTool, el certificado, el contenedor, el PIN, el token o la firma no están disponibles.

La finalización de la marca de tiempo reintenta solo un comando de marca de tiempo que salió normalmente devolviendo fallo o aviso, como máximo tres veces con retardos de uno y dos segundos. Cada intento parte de la misma firma primaria verificada. Los errores de lanzamiento, la terminación incierta y los fallos de verificación se detienen inmediatamente. SignTool opera sobre rutas privadas cortas; la publicación copia los bytes verificados al volumen de destino antes del reemplazo atómico. Se requieren la confianza final de Windows, el certificado, la marca de tiempo y la igualdad normalizada del archivo completo. El agotamiento detiene el empaquetado y preserva la evidencia sin otra llamada hardware. Ver la [decisión de finalización de firmas](../../.agents/notes/implemented/process/2026-09-17-windows-signature-completion.md).

El PIN no puede contener `]`, una comilla ni un salto de línea porque esos caracteres delimitan el valor `/kc` de SafeNet o su argumento CMD. El CMD deshabilita la expansión retardada para que un PIN que contiene `!` llegue a SafeNet sin cambios. El empaquetado retiene todos los campos `DSH_DESKTOP_WINDOWS_*` de los subprocesos de compilación y de preparación del runtime, da al preflight de firma, a las etapas dedicadas de firma del runtime y a electron-builder solo las cuatro entradas configuradas, da al CMD de firma solo los campos de firma validados en un entorno por lo demás depurado, limpia esos campos antes de que arranque SignTool, y redacta los diagnósticos de SignTool. SafeNet sigue requiriendo el PIN en la línea de comandos del proceso SignTool. El `.env.windows` local almacena el PIN en texto plano y necesita acceso restringido al archivo; CI usa un archivo temporal y lo elimina tras el job. No confirmar ni compartir su contenido ni imprimir credenciales en los logs. Las comprobaciones de configuración no consumen intentos de PIN del token; la firma sigue deteniendo el lote en su primer fallo.

Este comando de diagnóstico es un punto de parada alternativo, no la primera mitad de una compilación de dos comandos. Cada comando de paquete compila el repositorio, empaqueta los cierres de producción propios enraizados en dsh y el Host privado de Desktop, y prepara la distribución de Electron del destino y la CLI de pnpm. `prepare:dsh` instala el grafo de producción una vez en tiempo de compilación, prepara los paquetes materializados para que electron-builder los archive bajo `app.asar/dsh`, elimina los metadatos del gestor de paquetes y escribe `desktop-runtime.json` con las versiones de paquetes compartidos y los hashes finales de archivos. Los ejecutables y bibliotecas nativos se desempaquetan junto al ASAR; Python, el Node independiente y pnpm permanecen en recursos de runtime externos. El empaquetado de Windows comprueba cada PE preparado contra su entrada desempaquetada del ASAR y su copia en disco byte a byte idéntica, incluidas las compilaciones sin firma. Las reglas glob del constructor hacen coincidir las llaves en los nombres de archivo PE como comodines de un carácter, por lo que un archivo vecino coincidente también puede desempaquetarse. La prueba de humo del runtime preparado usa el descriptor verificado del destino en lugar de la arquitectura del host de compilación. El instalador firmado, la notarización, la actualización instalada y la cualificación de módulos nativos específica del destino requieren el entorno de lanzamiento.

El hook de firma verifica el feed exacto y el directorio de caché del actualizador. Un artefacto desempaquetado contiene Electron, el árbol de producción dsh materializado, pnpm y la aplicación shell. ## Actualizaciones

En Windows, la confirmación de actualización descargada explica que la aplicación se cierra durante la instalación, se reabre automáticamente y no debe lanzarse de nuevo mientras se actualiza. Un reinicio del instalador que lleva `--updated` eleva y enfoca la ventana principal una vez cuando el arranque abre el espacio de trabajo directamente, sin habilitar siempre encima. El arranque en la página de bienvenida descarta esa solicitud para que un login posterior conserve su comportamiento normal de activación. Los lanzamientos ordinarios y las demás plataformas no usan este paso de primer plano.

Los overlays nativos de actualización esperan un documento listo y un padre visible, y reaparecen cuando ese padre se muestra de nuevo. Cerrar un overlay libera su interceptación de entrada y los listeners del padre. La [cualificación de ventana local](tests/README.es.md#verification-overlay) ejercita estas transiciones sin arrancar un espacio de trabajo.

Las aplicaciones empaquetadas con feed de actualización comprueban el Nightly fijo de forma asíncrona en el arranque. El sondeo ordinario usa un intervalo base de diez minutos con un jitter de ±20 % muestreado independientemente. Cada fallo de comprobación duplica el retardo base hasta una hora; el éxito lo restablece. El retardo aleatorio está acotado por ese tope y empieza después de que todos los llamantes unidos se asientan. Las comprobaciones de primer plano y de reanudación del sistema respetan el mismo plazo monotónico; el elemento de menú localizado Buscar actualizaciones, incluido en el menú Aplicación del título de Windows, se ejecuta inmediatamente y se une a una comprobación en vuelo. Una política obligatoria recién recibida también solicita una comprobación de feed inmediata. Las comprobaciones automáticas nunca abren diálogos ni descargan paquetes. Las comprobaciones manuales muestran retroalimentación de comprobación, fallo o sin actualización con la versión instalada. Los diálogos ordinarios de actualización aparecen y desaparecen con fundido en su sitio; los avisos consecutivos reemplazan el contenido de la tarjeta y restablecen su posición de scroll conservando el fondo translúcido oscuro sin desenfocar la página padre.

`DSH_DESKTOP_UPDATE_CHECK_INTERVAL_MS` configura el intervalo base ordinario, y `DSH_DESKTOP_UPDATE_CHECK_MAX_BACKOFF_MS` configura el tope; ambos aceptan milisegundos enteros de 1000 a 2147483647, con el tope al menos igual al intervalo. Un tope omitido toma por defecto el mayor de una hora y el intervalo. `DSH_DESKTOP_UPDATE_CHECK_JITTER` establece la fracción de jitter de 0 a 1, con `0.2` por defecto; el retardo final es de al menos un segundo y nunca excede el tope. Estos ajustes no cambian el sondeo de política obligatoria ni autorizan reintentos de descarga.

La fila de cuenta de la esquina inferior izquierda muestra la disponibilidad localizada, un spinner con porcentaje de descarga, verificación, disponibilidad, o una acción persistente de reintento en rojo con un tooltip accesible. Este texto incrustado en Web sigue el idioma activo dentro de la aplicación; los diálogos nativos usan la locale del shell de Desktop. La barra lateral contraída muestra un punto en su botón superior de expansión. El estado de la conexión tiene prioridad. Seleccionar un lanzamiento disponible empieza a descargar inmediatamente. Una preparación con éxito abre automáticamente una confirmación de reinicio propiedad del shell; cerrarla conserva la disponibilidad sin reabrir el diálogo. Seleccionar la entrada lista abre la confirmación de nuevo. Los agents en ejecución, la entrada en cola y los jobs en ejecución o deteniéndose disparan un aviso de interrupción en esa confirmación. Las solicitudes de API por sí solas no disparan el aviso. Tras la aprobación, el Host bloquea las solicitudes nuevas, drena las solicitudes admitidas y vuelve a comprobar las tareas, incluido el trabajo creado por una escritura admitida. Un drenaje que excede el plazo de la solicitud de control rechaza la instalación y desbloquea la admisión. Un estado de tareas desconocido, trabajo recién iniciado sin aprobación de interrupción o un desmontaje ordenado sin éxito impide la instalación. La salida ordinaria pregunta por el trabajo interrumpible como se describe en Cerrar la ventana y salir, después oculta la ventana del producto antes de detener el Host, ignora las nuevas solicitudes de foco durante el desmontaje, y nunca instala una actualización. El siguiente lanzamiento reconcilia el runtime vinculado a la versión a través de la ruta de arranque y recuperación existente.

Si el desmontaje de tareas falla tras la salida confirmada del Host, se rechaza la instalación y el shell restaura el Host de la versión actual antes de permitir otra confirmación de reinicio. Un fallo de lanzamiento del instalador tras una parada limpia del Host usa la misma recuperación. Después de que el Host de reemplazo se autentica, el shell recarga la URL de aplicación existente para que la página Web obtenga su puerto, cookie e inyecciones de arranque actuales; un fallo de carga de página abre la recuperación fatal nativa. Una salida de proceso no confirmada nunca permite un Host de reemplazo. El destino descargado permanece disponible para reintentar. Una política obligatoria conocida sigue bloqueando durante toda la recuperación; una restauración del Host sin éxito abre el diálogo nativo de recuperación fatal.

La salida confirmada del Host sin un desmontaje de tareas con éxito muestra orientación de recuperación localizada tanto en los diálogos ordinarios como en los obligatorios de actualización. Una causa de preparación tipada selecciona esa orientación en cada locale; cambiar el texto traducido no puede reclasificar el fallo. «Ver detalles técnicos» está contraído por defecto y expone solo el estado de salida, la señal, el reconocimiento de apagado y los datos del plazo, no el stderr de los plugins. Expandirlo ni reintenta ni autoriza la instalación.

### Política de actualización obligatoria

La [decisión del cliente obligatorio](../../.agents/notes/implemented/feature/2026-09-11-desktop-mandatory-update-client.md) posee el sondeo de política y la ventana de bloqueo. El empaquetado lee `.env.windows` o `.env.macos`: `DSH_DESKTOP_AUTO_UPDATE_ENV=test` (el valor por defecto) selecciona `DSH_DESKTOP_MANDATORY_UPDATE_TEST_ORIGIN`; `production` selecciona `DSH_DESKTOP_MANDATORY_UPDATE_PROD_ORIGIN`. Las plantillas dejan ambos orígenes en blanco; rellenar el origen del despliegue seleccionado en el archivo dotenv local ignorado. El origen seleccionado es necesario antes de la preparación o la firma, incluidas las compilaciones sin firma y de solo preparación; el origen no seleccionado es opcional. Estos ajustes nunca recurren al entorno padre ni al otro despliegue. El empaquetado incrusta la política seleccionada con el ID de aplicación; las aplicaciones empaquetadas ignoran los overrides en runtime.

El JSON de `DSH_DESKTOP_MANDATORY_UPDATE_CONFIG` aporta orígenes de login de prueba y opciones opcionales de sondeo y página de descarga; el empaquetado rechaza `origin` y `authentication` en su interior. La lista de páginas permitidas toma por defecto el origen del servicio seleccionado; permitir explícitamente otros orígenes aprobados de páginas de descarga cuando sea necesario. Las compilaciones de prueba seleccionan `feishu-test` y requieren `allowedAuthOrigins` en `DSH_DESKTOP_MANDATORY_UPDATE_CONFIG`; producción selecciona `anonymous` y rechaza ese campo. Cada origen de login debe ser un origen HTTPS sin credenciales, ruta, query ni fragmento. La ventana de login permite la navegación de documentos solo al origen de política seleccionado y a estos orígenes configurados. Las solicitudes de política rechazan las redirecciones; solo la autenticación de prueba lleva cookies de puerta de enlace. El desarrollo sin empaquetar, en cambio, lee un JSON de política completo de esta variable y requiere `DSH_DESKTOP_APP_ID`; el JSON ausente deshabilita las consultas de política de desarrollo, y solo el desarrollo anónimo permite HTTP `127.0.0.1`. Una comprobación ordinaria iniciada por el usuario dispara trabajo de política concurrentemente pero nunca espera ni reporta un fallo de política. Solo una decisión de bloqueo confirmada cancela los diálogos ordinarios. La autenticación de prueba espera hasta que el diálogo ordinario activo termina, y la cancelación o el fallo no descarta el resultado del actualizador.

| Campo de política resuelto | Significado y valor por defecto |
|---|---|
| `origin` | Origen HTTPS de API requerido, sin credenciales, ruta, query ni fragmento; las solicitudes usan `/api/v0/check_client_update` |
| `allowedPageOrigins` | Array no vacío de orígenes HTTPS exactos; el empaquetado toma por defecto el origen de API seleccionado; los subdominios y puertos alternativos no están implícitos |
| `authentication` | El empaquetado selecciona `feishu-test` para prueba y `anonymous` para producción; el desarrollo sin empaquetar toma `anonymous` por defecto |
| `allowedAuthOrigins` | Array no vacío de orígenes HTTPS exactos de documentos de login para la autenticación de prueba; prohibido en producción |
| `intervalMs` | Intervalo de sondeo; por defecto `600000` |
| `timeoutMs` | Plazo de solicitud; por defecto `15000` |
| `maxBackoffMs` | Intervalo máximo de solicitud fallida incluido el jitter; por defecto `3600000`, al menos `intervalMs` |
| `jitter` | Fracción de intervalo adicional aleatoria; por defecto `0.2`, rango permitido de `0` a `1` |

Las duraciones son enteros de 1000 a 2147483647 milisegundos. El sondeo de arranque y el programado son independientes de las solicitudes de negocio; las comprobaciones de primer plano y reanudación respetan el siguiente momento debido, mientras que las comprobaciones manuales lo omiten y se unen a cualquier solicitud en vuelo. El cliente envía la plataforma instalada, la arquitectura, DSH_CLIENT_VERSION, la versión de dsh incluida, la locale actual y el desplazamiento UTC, un bundle ID vacío y el Nightly fijo. No usa credenciales de login de negocio ni ID de instalación.

Con `feishu-test`, una respuesta JSON HTTP 401 que contiene `error.code: "UNAUTHENTICATED"` ofrece login durante las comprobaciones iniciadas por el usuario y la comprobación de arranque inicial de la aplicación empaquetada, sin esperar al backend local. Una explicación localizada identifica la compilación de prueba, la necesidad de autenticación de Feishu y que el login ni descarga ni instala actualizaciones. La confirmación cierra la explicación antes de abrir una ventana con sandbox en la raíz del origen configurado, no en una URL de login proporcionada por la respuesta. Las comprobaciones concurrentes reutilizan toda la operación de confirmación y login y enfocan su ventana existente. Pulsar F12 en la ventana de login de prueba para abrir DevTools separadas para el diagnóstico. La cancelación no dispara avisos repetidos de las comprobaciones periódicas o de primer plano; los usuarios pueden reintentar manualmente.

Las solicitudes de login y de política comparten una sesión en memoria, separada de las ventanas del producto y del actualizador; el reinicio requiere un login nuevo. Cerrar cancela el login, y un fallo de navegación proporciona orientación de reintento localizada. Volver al servicio dispara una consulta de política nueva; una redirección, una cookie o un HTTP 422 no es una decisión de política válida. La cancelación, la expiración y las respuestas inválidas conservan cualquier bloqueo obligatorio conocido. Los resultados fijos de login aparecen en los diagnósticos del proceso y en el journal de actualización opcional; el controlador de login no registra cookies, parámetros OAuth ni texto de error remoto. La integración en vivo de la puerta de enlace y la API de Harness y la cualificación de login de macOS permanecen sin verificar.

Un `40005` aplanado abre un modal propiedad del shell y rechaza las mutaciones de plugins posteriores sin detener las tareas del Host existentes. El título y el detalle del servidor son texto plano opcional y recurren al texto del cliente; una URL de descarga ausente o no aprobada oculta las acciones de página externa sin limpiar el bloqueo. En macOS el overlay obligatorio aparece y desaparece con fundido en su sitio, conserva su fondo durante los cambios de estado de actualización y redirige el foco y la entrada de teclado de la ventana padre al overlay. En Windows el preload de aplicación aislado monta un frame de origen shell dentro de la ventana principal, cubriendo el contenido bajo el título de 40 DIP con un fondo y un diálogo. Bloquea la entrada de la página de fondo sin crear otra ventana nativa; mover y maximizar afectan solo a la ventana principal. Los menús del título conservan la operación de ratón y teclado; los controles Web del título siguen siendo alcanzables. El DOM compartido es una restricción de presentación, no un límite de seguridad: los scripts del producto pueden ocultar el overlay pero no pueden limpiar la política del proceso principal ni autorizar la instalación a través de él. Las acciones y el estado de actualización usan un MessageChannel privado entre el preload aislado y el frame del shell. El padre permanece habilitado para los controles nativos de mover, redimensionar, minimizar, maximizar y cerrar. Cerrar la aplicación realiza la limpieza sin limpiar el requisito de actualización; Esc no descarta el overlay. Una vez aprobada la instalación, la salida propiedad del instalador libera el modal antes de que Electron cierre las ventanas. La descarga, la verificación de archivos incluida la preparación, la inspección de tareas y la confirmación de instalación comparten este mismo modal. Solo la segunda aprobación del usuario permite el desmontaje de tareas y la instalación; el aplazamiento conserva el bloqueo y el paquete. La retroalimentación de reinicio menciona la detención de tareas solo cuando existen tareas afectadas. La política no se persiste entre reinicios de la aplicación, y las respuestas de política nunca revocan ni reemplazan un artefacto del actualizador.

Los fallos conservan el bloqueo, la orientación de reintento localizada y los diagnósticos plegados dentro del modal. La acción de página de descarga permitida aparece en los estados de recuperación, no junto a la descarga o instalación normal. Solicitar el navegador expone inmediatamente una alternativa de copia incluso mientras la solicitud del SO está pendiente; una solicitud resuelta no prueba que la página se abrió. Un fallo de copia revela la dirección completa de solo lectura para copia manual. Los resultados del navegador y del portapapeles no sobrescriben los errores del actualizador. Solo una respuesta nueva válida de no forzado limpia el bloqueo; la comprobación del menú superior sigue disponible mientras hay bloqueo.

La confirmación de instalación obligatoria en segundo plano solicita atención de la barra de tareas de Windows o un rebote informativo del Dock de macOS más una notificación silenciosa por episodio de disponibilidad. No restaura ni enfoca la app. Los clics en la notificación solo vuelven a la confirmación actual. El retorno al primer plano, la instalación, la limpieza de la política y el apagado limpian los recordatorios propios. Los permisos del sistema y los modos de concentración pueden suprimir las notificaciones; la cualificación de notificaciones de Windows y macOS instaladas sigue siendo necesaria.

### Cualificación local del actualizador

Las solicitudes HTTP ordinarias de actualización tienen un plazo de inactividad por conexión: la ausencia de cabeceras de respuesta o de más bytes de respuesta durante `60000` ms hace fallar la operación. `DSH_DESKTOP_UPDATE_HTTP_IDLE_TIMEOUT_MS` acepta un entero de `1000` a `2147483647` para ajustarlo; las descargas activas no tienen plazo de duración total. Las descargas fallidas conservan el indicador de reintento y requieren otra acción del usuario.

En Windows con las dependencias del espacio de trabajo instaladas, ejecutar este comando desde la raíz del repositorio:

```sh
node apps/desktop/node_modules/pnpm/bin/pnpm.mjs --dir apps/desktop run test:updates:local
```

El comando compila el shell de Desktop y ejecuta su coordinador con solicitudes HTTP reales de Electron y `NsisUpdater` contra un servidor loopback privado. Comprueba las descargas completas autorizadas por el usuario, el rechazo de SHA-512, el reintento explícito, la fusión de solicitudes concurrentes, el reemplazo de feeds y el traspaso de instalación. También abre el renderer real de actualización obligatoria con su preload con sandbox y comprueba las acciones de botones, la prevención de cierre y Esc, el contenido de solo texto, una solicitud de política estancada y la limpieza de la política. El éxito imprime `LOCAL_UPDATER_RESULT` y sale con código cero; un fallo funcional sale con código distinto de cero. Cada invocación posee un puerto aleatorio y un directorio temporal de datos de usuario y caché, cierra el listener, espera la salida de Electron y elimina sus archivos temporales. Los reportes y las capturas de pantalla disponibles permanecen en un directorio único `.desktop-build/qualification/local-updater-*`. El fallo de captura de pantalla se registra por separado, nunca se reporta como aceptación visual. No se requieren credenciales de COS ni de firma.

Los bytes descargados son inertes, y la llamada de instalación se registra en lugar de ejecutarse. La prueba sustituye la apertura del navegador y la escritura del portapapeles para evitar la navegación externa y los cambios del portapapeles. No arranca el espacio de trabajo completo del producto, no cualifica un instalador o reinicio real, no verifica las firmas del editor ni ejercita las actualizaciones diferenciales ni macOS. Las solicitudes de política estancadas, las solicitudes de feed y las transferencias de payload ejercitan plazos y recuperación reales. El diálogo ordinario real verifica la carga del preload aislado, la geometría de la tarjeta, una página padre sin filtrar, la cancelación, las elecciones de aviso de tareas y la aprobación explícita de instalación; las pruebas de componentes de la fila de cuenta aportan evidencia separada. La [decisión de cualificación local](../../.agents/notes/implemented/testing/2026-09-10-desktop-local-updater-qualification.md) y el [registro de verificación](tests/README.es.md) preservan estos límites; los requisitos de lanzamiento de producción no cambian.

## Overrides de desarrollo de bajo nivel

Un proceso de Electron sin empaquetar usa `.desktop-build/development/project` bajo su directorio de aplicación como su proyecto de desarrollo. `DSH_DESKTOP_PNPM_ENTRY` y `DSH_DESKTOP_DSH_DIR` son overrides opcionales con valores por defecto de ruta de aplicación. `DSH_DESKTOP_PRIMARY_RUNTIME_DIR` es obligatorio para cada lanzamiento sin empaquetar: los lanzadores de desarrollo (`dev:desktop`, `start:desktop` y el runner de cualificación de actualización del espacio de trabajo) lo establecen al directorio del runtime primario del destino que prepararon, y un lanzamiento sin él falla con el diálogo de arranque fatal. El lanzador debe establecerlo porque el shell no puede derivar ese directorio de `process.arch`: el destino de compilación fija Windows a x64 mientras el host puede ser arm64. Las aplicaciones empaquetadas ignoran estas variables, resuelven los recursos firmados desde `process.resourcesPath` y usan el perfil de Desktop gestionado.

## Limitaciones conocidas

- El inicio de sesión de cuenta no está conectado; el botón Iniciar sesión está deshabilitado. El renderizado del material de Windows sigue requiriendo QA de plataforma.

- La firma de lanzamiento, la notarización, el alojamiento de actualizaciones y la cualificación de artefactos instalados de versiones anteriores requieren el entorno de lanzamiento de producción.
- Los scripts de ciclo de vida de dependencias siguen los permisos de compilación de pnpm; Desktop no proporciona ningún diálogo de aprobación separado.
- El shell de escritorio comparte sesiones, configuración, credenciales, espacios de trabajo y almacenamiento bajo `$DSH_HOME` con el dsh de la CLI, mientras que los paquetes ejecutables, la activación de plugins y los lockfiles permanecen separados.
- El arranque sin empaquetar en un host Electron win32-arm64 ahora tiene éxito, pero el payload sigue siendo x64: la comprobación de arquitectura en `packages/skill/tool-workspace-dependencies/src/index.ts` compara la arquitectura del payload registrada contra el `process.arch` del host, por lo que la tool `load_workspace_dependencies` aún puede rechazar el runtime primario.
- Linux es solo sin firma, sin feed de actualización ni actualizaciones automáticas.
- Linux no tiene icono de bandeja; un segundo lanzamiento vuelve a mostrar la ventana, y no aparecen señales de atención de actualización.
- Linux no ejecuta el cliente de política de actualización obligatoria y no ofrece instalación del comando de terminal `dsh`.

El método de preload `dshOnboarding.hasApiKey()` solo de la app devuelve el booleano actual de presencia de clave de API del backend de bienvenida; el login nativo y el onboarding comparten el descubrimiento de credenciales, y solo el frame principal de la aplicación propia puede invocarlo.

Iniciar sesión abre la página de la plataforma configurada en el navegador del sistema. El Host posee PKCE y un callback loopback temporal, guarda la credencial antes de entrar en el espacio de trabajo y redirige el navegador a la página de finalización de la plataforma. Los enlaces de autorización abiertos y copiados llevan el tema efectivo de Desktop como `theme=light` o `theme=dark`; `system` se resuelve en el momento de la acción. Cancelar retira el intento local aunque la página de la plataforma lo apruebe después. La configuración ofrece Cierre de sesión de cuenta; sin una clave de API separada, cerrar sesión vuelve a la ventana de bienvenida. Un inicio de sesión en el navegador con éxito cambia de Welcome al espacio de trabajo sin activar la aplicación; el enlace dsh://open de la página de finalización la trae al primer plano. Las aplicaciones empaquetadas registran dsh://open para mostrar la ventana sin pasar credenciales. En macOS, el lanzador de desarrollo prepara un `Harness Dev.app` firmado ad hoc bajo `.desktop-build/development`, declara `dsh` en su Info.plist y lo registra con Launch Services. Carga el espacio de trabajo actual y registra el home de desarrollo seleccionado, la ruta de datos del navegador y los ajustes de depuración para los arranques en frío. Arrancar este bundle lo convierte en el manejador por defecto de `dsh://`; arrancar la aplicación empaquetada registra de nuevo el manejador empaquetado. El bundle generado no contiene tokens de cuenta y requiere que el espacio de trabajo y el runtime preparado sigan disponibles.

Cuando una cuenta expirada vuelve a Welcome, el proceso principal retiene una notificación única hasta que el renderer la solicita por IPC de ventana propia. Recargar Welcome no repite el aviso; el cierre de sesión manual y el arranque en frío no lo crean.

Un login expirado muestra un encabezado de expiración con acciones explícitas Iniciar sesión de nuevo y Añadir clave de API. Abrir el formulario de clave de API descarta la vista de autorización; las notificaciones tardías de estado de cuenta no reemplazan una entrada de clave en curso.

Las vistas de Platform incrustadas permanecen ocultas hasta que la carga del documento termina para que el indicador de carga del renderer siga visible. Cerrar o reemplazar una vista pendiente impide que aparezca después. Recargar o reemplazar el documento de aplicación propietario, la terminación del renderer y el cierre de la ventana también destruyen la vista nativa sin depender de la limpieza de React.

Las cabeceras privadas de despliegue de Platform las inyecta la sesión de navegador incrustado solo para su origen configurado, incluidas las solicitudes de documentos y de API. Los overrides de cookies se fusionan por nombre. Las solicitudes entre orígenes descartan las cabeceras de despliegue; el bootstrap solo expone el origen, el token y el idioma resuelto.

La configuración `embeddedPageDist` del proveedor de cuentas añade un parámetro de query `dist` a las URL incrustadas de Uso y Recarga. Su valor por defecto es vacío; los selectores de rama de frontend privados pertenecen al parche del perfil local. No cambia las URL de la API ni la entrega de credenciales.
